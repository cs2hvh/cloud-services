Build Sheet

Everything the platform stands on, in the order it has to be built, with the command for each step and what breaks if you skip it. Every step is marked for what a host migration would cost it — because the reason to write this down is that one day some of it moves.

Portable
Survives a move as it stands. Standard Kubernetes, S3, Postgres.
Rewrite
Same shape, different API. Bounded work, no design decisions.
Decision
Not a task. The substrate's own limits force the answer.

The secrets directory

Three files live outside every git repository. Nothing in the codebase reads a credential from anywhere else. 

<secrets-dir>/kubeconfig-v2-dev.yaml   # cluster access — written by step 1
<secrets-dir>/origin-v2.crt           # Cloudflare Origin CA cert
<secrets-dir>/origin-v2.key           # its private key
<secrets-dir>/env-master-key.txt      # AES-256 root for every customer secret

The master key has no recovery

V2_ENV_MASTER_KEY is the root of the HKDF that derives a key per project. It encrypts every customer environment variable and every stored GitLab and Bitbucket OAuth token. Lose it and all of that is permanently unreadable; leak it and all of it is readable. 44 characters, base64 of 32 bytes. Mode 600, and never in a repository, a ticket or a chat.

The build order

Each step depends on the one before it. Every script is idempotent and every script has a dry run — run without --apply first, always.

01
The database schemaportable

Apply the migrations to a Postgres with the paas schema. This comes first because step 2 refuses to run without it — provisioning that cannot record what it created is how a cluster ends up running with nothing tracking it.

Plain Postgres with RLS. Nothing here is Supabase-specific except auth.users, which team ownership references.

02
The clusterrewrite
node --env-file=.env --env-file=.env.local scripts/v2/provision-cluster.ts
node --env-file=.env --env-file=.env.local scripts/v2/provision-cluster.ts --apply

Creates an LKE cluster tagged ahura-v2 — idempotent, so an existing tagged cluster in the region is reused rather than duplicated. It checks the region really offers Kubernetes, VPCs and NodeBalancers before it starts, and writes the kubeconfig to the secrets directory.

Two node pools, and the split is the isolation model. system carries the gateway, registry and observability; runtime is tainted NoSchedule and is the only pool that will carry gVisor. Customer pods never land on system.

There is deliberately no build pool — see step 9.

Decide HA before you create, not after

The HA control plane costs $60/month and enabling it later is irreversible and recreates every node. The dev cluster runs without it. The first cluster that will ever serve production must be created with it already on — there is no upgrade path, only a rebuild.

03
The platform namespace and registryportable
node --env-file=.env --env-file=.env.local scripts/v2/bootstrap-cluster.ts --apply

Creates ahura-system, the R2 credential secret, and Docker Distribution backed by R2. The registry is never publicly exposed; it is reachable only inside the cluster.

It also installs a registry-proxy DaemonSet, and the reason is worth knowing before you delete it: the kubelet pulls over 127.0.0.1 because containerd resolves image hostnames with the node's resolver, which cannot see *.svc.cluster.local — and LKE gives no way to edit node configuration. The proxy exists because that door is shut.

04
The sandboxdecision
node --env-file=.env --env-file=.env.local scripts/v2/install-gvisor.ts --apply

Installs gVisor onto the runtime pool and proves it by reading the kernel a tenant pod reports — Linux version 4.19.0-gvisor, not the host's. It restarts containerd on that node, which restarts what is running there.

This is a decision the substrate made, not a preference. Linode has no nested virtualisation and sells no bare metal, so Kata, Firecracker and every microVM design are impossible. gVisor is a userspace kernel and needs no /dev/kvm. On a host that does offer nested virtualisation, this step and step 9 both change completely.

05
The gateway and the public addressrewrite
node --env-file=.env --env-file=.env.local scripts/v2/install-gateway.ts --apply

Installs Traefik and a LoadBalancer Service, which makes Linode create a NodeBalancer — about $10/month. It reports the public IP it lands on. Write that down: it is what DNS points at, and what the firewall in step 10 protects.

It also loads the Cloudflare Origin CA certificate from the secrets directory into a Kubernetes Secret. One certificate covers the whole wildcard, so no per-app certificate exists and there is no Let's Encrypt rate limit to hit.

06
Metricsportable
node --env-file=.env --env-file=.env.local scripts/v2/install-metrics-server.ts --apply

Stock metrics-server, hand-authored rather than pulled from a chart. Usage metering reads metrics.k8s.io to tell an idle app from a busy one; without this, warm-fraction and per-app CPU are simply absent.

07
The activatorportable
node --env-file=.env --env-file=.env.local scripts/v2/install-activator.ts --apply

Holds the first request to a sleeping app, wakes it, and proxies once it is ready. It is verified by asking it to serve a request, not by asking Kubernetes whether it looks ready.

Only needed if scale-to-zero will ever be switched on — but install it first. An app that scales down and cannot come back is just an app that is down.

08
The scheduled sweepsportable
node --env-file=.env --env-file=.env.local scripts/v2/install-sweeps.ts --apply

Ten CronJobs on staggered minutes. Each gets its own ServiceAccount and only the Secret it needs — no sweep pod ever holds more than one external credential. That is why there are ten narrow jobs and not one wide one: the aggregator that would need all of them is deliberately never scheduled, because concentrating every platform credential in one pod is precisely the shape that gave v1 a cluster-wide compromise.

Two of the ten write: meter-apps charges the hour, and project-teardown removes deleted projects' workloads. Enable teardown first and let it converge to zero before metering goes on — billing an app whose pods were never removed is v1's defect exactly.

09
Nothing — the build tier needs no setupdecision

There is no build cluster, no runner pool and no CI to install. Every build leases its own throwaway Linode, runs rootless BuildKit on it, and destroys it. The isolation boundary is Linode's own hypervisor — the same one separating Linode's customers from each other.

This exists because of step 4's constraint. With no nested virtualisation available, renting a whole machine is the only way to get a hardware boundary around untrusted build code. It costs about $0.002 per build.

On a host with nested virtualisation this design is unnecessary and a microVM runner inside the cluster would be cheaper and faster. Listed as a step precisely so nobody reimplements it after moving somewhere it is not needed.

10
Close the originrewrite
node --env-file=.env --env-file=.env.local scripts/v2/origin-lockdown.ts         # probe only
node --env-file=.env --env-file=.env.local scripts/v2/origin-lockdown-apply.ts --apply
node --env-file=.env --env-file=.env.local scripts/v2/origin-lockdown-apply.ts --detach

Until this runs, the NodeBalancer answers on its public IP and anyone who learns that address walks straight past Cloudflare's WAF and rate limiting. A Linode Cloud Firewall permitting Cloudflare's ranges only closes it.

The script is not one curl because of what surrounds the call: it probes every live hostname first so "it was already broken" and "we broke it" cannot be confused afterwards, attaches, probes again, and detaches automatically if anything that was answering has stopped. A revert nobody is awake to perform is not a revert.

Do not trust the firewall's label

The live firewall is named UNATTACHED-cf-only-origin from when it genuinely was unattached. It is attached. Trust the device count, not the name — and verify with the probe script, which tests behaviour rather than reading labels.

Wiring the edge

Cloudflare, in the order the pieces depend on each other.

#Set upWhy it is in this order
1Zone for your apex domainEverything else hangs off it.
2Origin CA certificate for *.<domain>Needed by step 5 above. Issued from the Cloudflare dashboard, valid up to 15 years. Save both halves into the secrets directory.
3Proxied A record per app hostname → the NodeBalancer IPCreated automatically by the deploy path. Platform subdomains cost zero custom hostnames — the single biggest cost avoidance in the design.
4Fallback origin — one hostname customer domains CNAME toCloudflare for SaaS routes every customer domain through it. Ours is fallback.<domain>, and it is a reserved label so no tenant can claim it.

Two limits to know before you sell against them

Per-tenant WAF and more than one rate-limit rule are Enterprise-only. On the free plan you get one rate-limit rule for the whole platform and no per-tenant isolation at the edge. At any real number of untrusted tenants that is a requirement, not a nicety — and it is a commercial decision, not something the code can route around.

Absolute paths are the trap this platform has fallen into twice

Four of these are paths, not values: the kubeconfig, both halves of the origin certificate, and the GitHub App key. A path that is right on a developer's machine is wrong on the server, and nothing reads them at startup — they fail at the first request that needs them, which is never the request anybody is watching.

It has happened twice here. The GitHub App key shipped as a Windows path onto a Linux box. And V2_KUBECONFIG was not set at all, so five call sites fell through to a hardcoded default — the server had no cluster access whatsoever for its first day, and the only symptom was deletes reporting that they could not tear anything down.

When you move hosts: grep the source, not just the config. A missing variable has nothing to grep for.

Git providers

All three are optional and independent — the platform runs with only one configured, and public repositories deploy on any provider with no credential at all. Callback URLs are <app-url>/api/v2/<provider>/callback.

ProviderCreateScopes
GitHubA GitHub App, not an OAuth appContents, Metadata; webhook on push
GitLabUser settings → Applicationsapi, read_user
BitbucketWorkspace settings → OAuth clientsAccount: read · Repositories: read · Webhooks: read+write

GitHub stores no credential — tokens are minted per request from the App key and expire in an hour. GitLab and Bitbucket are OAuth, so the platform holds a refreshable token for as long as the connection lives. That asymmetry means connecting GitLab gives us a durable credential to a customer's account and connecting GitHub does not, and it is why those columns are encrypted separately from environment variables.

Running it

Everything above describes the platform as code. This is the platform as a running system: what is alive on the host, what restarts it, and how to run the whole thing yourself.

The three services

Three long-lived processes, all systemd units, all running from the same checkout at /root/cloud-services. The third is the one nobody thinks about, and it is the one that took five days to notice was wrong.

UnitWhat it isIf it stops
ahura-web The Next.js app — dashboard and every API route. server.ts, not next start. Loud. The site is down and everyone knows within a minute.
ahura-cron The hourly billing sweep, on a .timer. Silent. Nothing is billed. See the note in its own unit file — this exact failure ran for six days.
ahura-build-worker Polls paas.deployments for queued rows and builds them. Every webhook and every Deploy button ends here. Silent. Deploys sit in queued forever. No error, no timeout, no alert.

A green deploy is not evidence that the build path changed

The build worker had no unit at all for its first weeks. It ran as a hand-started process, and deploy.sh restarted only the web app and the cron — so it kept executing whatever revision it had been launched with, indefinitely.

Five days of build-path fixes shipped to dev, deployed green, and never ran: the build-time secret mount, the customer-facing error wording, and the Next.js output:'standalone' layout. All three were "live". None executed. It surfaced from a customer's failed build, not from anything being monitored.

To verify a build-path change, read a fresh build's generated Dockerfile — it is printed at the top of every build log. systemctl status tells you a process is running; it says nothing about which revision it is running.

Two env files, and the difference is not cosmetic

FileHoldsLoaded by
.env Supabase, and everything v1 needs. Next.js automatically · node --env-file=.env
.env.local Every V2_* variable — R2, Linode, Cloudflare, the git apps, the master key. Next.js automatically · node only if you name it

node --env-file=.env does not imply .env.local

Next.js loads both, which is why the web app has these variables and why the split is easy to forget. Plain node loads exactly what you name, in order, last one winning.

A systemd unit written with a single --env-file=.env starts cleanly, reads not one V2_* variable, and dies on the first it needs — V2_R2_ENDPOINT — before it ever reads the queue. That is not hypothetical; it is how the build worker's first unit was written, by copying the billing sweep's, which needs none of them. Always both, and .env.local second: 

node --experimental-strip-types \
  --env-file=/root/cloud-services/.env \
  --env-file-if-exists=/root/cloud-services/.env.local \
  /root/cloud-services/scripts/v2/build-worker.ts

How a deploy happens

push to dev
  → .github/workflows/deploy.yml     # triggers on push to dev, or manual for any branch
  → SSH to the host                  # DEPLOY_HOST / DEPLOY_USER / DEPLOY_PASSWORD secrets
  → bash /root/deploy.sh dev
        git fetch + reset --hard origin/dev
        npm ci                       # only when package-lock.json changed, or --deps
        npm run build                # if this fails, NOTHING is restarted and the old build serves on
        systemctl restart ahura-web ahura-cron ahura-build-worker
        health check on 127.0.0.1:3000
  → refresh /root/deploy.sh from the repo
  → assert the build worker is active, or fail the run with its journal

/root/deploy.sh is a copy that lives outside the repo, deliberately, so git reset --hard cannot touch it mid-deploy. The cost is that it drifts: a fix to deploy/deploy.sh never reaches the script that actually runs. The workflow now re-copies it after every pull, which closes that loop — but if you are debugging a deploy, check you are reading the same file that ran.

One-time host setup

cp /root/cloud-services/deploy/deploy.sh /root/deploy.sh && chmod +x /root/deploy.sh
cp /root/cloud-services/deploy/systemd/ahura-*.service /etc/systemd/system/
cp /root/cloud-services/deploy/systemd/ahura-billing-sweep.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now ahura-build-worker
systemctl enable --now ahura-billing-sweep.timer

Never run two build workers

deployments.queued() is a plain select … where state = 'queued'. There is no atomic claim, no lease, no advisory lock. Two workers both see the same row and both build it — which means two build VMs leased and paid for, for one deployment, racing to write the same database row.

Kill any hand-started worker before enabling the unit, and never pkill a running one to "restart" it: builds have no resume, so a worker killed mid-build leaves its deployment stuck in building forever. Use systemctl restart, which stops it gracefully. If you ever want more than one worker, the claim has to become atomic first.

Running it yourself

Node 22.9 or newer — --experimental-strip-types needs 22.6 and --env-file-if-exists needs 22.9. Then: 

git clone <repo> && cd cloud-services
npm ci
# put .env and .env.local in the repo root — see "Wiring the application" above
npm run dev                          # tsx watch server.ts; PORT=3000 unless you set it

npm run dev runs the custom server in server.ts, not next dev — the WebSocket routes for VNC and GPU terminals are attached there and do not exist under plain next dev. Use npm run dev:fast only for UI work that touches neither.

To run the build worker against the queue from your own machine:

node --experimental-strip-types --env-file=.env --env-file-if-exists=.env.local \
  scripts/v2/build-worker.ts --once            # one pass, then exit

--once is the safe form. Without it the worker polls forever and competes with the one on the server for the same queue — see the warning above. Never leave a local worker running against production.

Tests need no cloud account:

npm run test:paas                    # ~1,100 unit tests; env files optional

A handful of encryption tests need V2_ENV_MASTER_KEY and will fail without it. Everything else — detection, Dockerfile generation, pricing, placement, the sweeps — runs offline.

There is no offline mode, and that is a design decision

You can run the control plane locally, but you cannot run the platform locally. Creating and deploying an app leases a real Linode, pushes to a real registry, and applies to a real cluster. There is no emulator and no dry-run substrate.

So "running it yourself" means pointing a local server at the same cloud resources — which is also why a local instance shares the production database and queue by default. If you want isolation you need a second Supabase project, a second cluster and a second R2 bucket, and at that point you are provisioning a second environment rather than running one locally. Until then, treat a local server as production with a different front end.

If this moves

What a migration actually costs, by layer. The short answer is that the control plane is portable and the substrate assumptions are not.

LayerCostWhat is involved
Control plane portable Postgres and a reconciler. Desired state in rows, level-triggered convergence, no imperative calls. Moves to any Postgres unchanged.
Kubernetes layer portable Namespaces, Deployments, Services, NetworkPolicy, Ingress — all stock objects as typed JSON. Runs on any conformant cluster.
Object storage portable R2 is reached with SigV4. Any S3-compatible store works by changing the endpoint.
Git providers portable Nothing host-specific. New OAuth apps with new callback URLs.
Compute API rewrite One client, four API groups: instances, LKE, NodeBalancers, regions. Bounded and mechanical — the shape is the same on every provider.
Edge rewrite DNS and certificates are generic. Cloudflare for SaaS custom hostnames are not — a move means finding an equivalent or building per-domain certificate issuance, which is the thing this design exists to avoid.
Build isolation decision The throwaway-VM model exists only because Linode offers no nested virtualisation and no bare metal. Somewhere that does, this is the wrong design — use microVMs in-cluster instead.
Sandbox decision gVisor for the same reason. With /dev/kvm available, Kata gives a stronger boundary at lower CPU cost.
Fleet sizing decision LKE caps pods per cluster at 1,000 (5,000 Enterprise), which is what forces a multi-cluster fleet and the placement layer. A host with a higher ceiling removes that requirement entirely.

The three questions to ask a replacement host

  1. Does it offer nested virtualisation or bare metal? Yes collapses two of the three decisions above and makes the build tier simpler and cheaper.
  2. What is the pod ceiling per cluster? This, not CPU or memory, is what determines how many clusters you operate.
  3. Is there a SaaS custom-hostname product? Without one, per-customer TLS becomes your problem, and that is the ceiling this whole edge design was chosen to remove.

Proving it works

One command. If it returns 200, every layer above is correctly wired.

node --experimental-strip-types --env-file-if-exists=.env.local \
  scripts/v2/framework-probe.ts pages/plain-html --provider gitlab --root public

It detects the framework, leases a build VM, builds, publishes to the registry, creates the alias, converges the cluster, creates DNS, waits for the hostname to answer, reports the status, and tears the whole thing down. A 200 exercises every step on this sheet.

Flags: --keep leaves it running, --team <slug> puts it in a specific team, --provider and --branch and --root do what they say.

And check nothing leaked

node --experimental-strip-types --env-file-if-exists=.env.local scripts/v3/fleet-drift.ts
node --experimental-strip-types --env-file-if-exists=.env.local scripts/v2/cluster-status.ts

The first prices what the provider is billing against what the control plane admits exists. The second reports nodes, namespaces and RuntimeClasses. Build VMs should be zero when no build is running; anything else is a leak and it is charging by the hour.
