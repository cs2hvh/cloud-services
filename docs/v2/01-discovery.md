## Per-subsystem audit

### Build & CI (platform-apps v1): Jenkins job generation, pipeline XML templating, Dockerfile selection/generation, image build+push, and build-status writeback

There is no Jenkinsfile anywhere. Every Jenkins job is a `config.xml` document built by TypeScript string interpolation at request time.

Job creation: `DeploymentService.deploy` (lib/services/deployment.ts:183-218) calls `JenkinsBuildAdapter.createJobAndTrigger` → `JenkinsService.createJob` (lib/services/jenkins.ts:301). It strips embedded git credentials (`sanitizeGitUrl`, jenkins.ts:54-60), picks a template via `selectPipeline`'s framework switch (jenkins.ts:1331-1400, 14 generators in lib/jenkins/pipelines/), then runs `hardenPipelineXml` (jenkins.ts:66-99) and upserts: `jenkins.job.config(jobName, pipeline)` first, `jenkins.job.create` only on 404 (jenkins.ts:346-375). Job name is always `${appName}-job`. It sleeps 1s and calls `jenkins.job.build({name, parameters:{COMMIT_SHA:'', GIT_AUTH_URL?}})` (jenkins.ts:384-390), discarding the returned queue id — the adapter then reports `buildNumber: 1` unconditionally (jenkins-build.adapter.ts:79-83).

Redeploy/auto-deploy instead call `updateJobConfig` (jenkins.ts:1407-1457), which regenerates the entire XML from the current DB state, then `triggerBuild` (jenkins.ts:236), which reads `lastBuild.number+1` as a fallback and polls `jenkins.queue.item` for up to 120s to learn the real build number (jenkins.ts:143-228).

`hardenPipelineXml` does exactly two things: it appends a `GIT_AUTH_URL` PasswordParameterDefinition when the XML already contains `</parameterDefinitions>`, and it regex-rewrites the `git clone --depth=1 --branch X URL . || git clone …` line into a single `GIT_TERMINAL_PROMPT=0 git clone --depth=1 --branch ${branchArg} "$REPO_URL" .` wrapped in `set +x`/`set -x` (jenkins.ts:83-94). `injectBuildRetentionOptions` (jenkins.ts:101-132) string-splices an `options { buildDiscarder(logRotator(...)) }` block before `\n  environment {`, skipping if the document already contains `buildDiscarder(`.

Dockerfile: chosen inside the build, not in TypeScript. Each `generate*DockerfileStage` emits `if [ -f Dockerfile ]; then … use it as-is … else cat > Dockerfile <<'DOCKERFILE_EOF'` (dockerfiles/index.ts:891-922, 937-1010). Node/Python/Java versions and package manager are detected by shell in the git container; `NODE_VERSION_PLACEHOLDER` is `sed`-replaced. Only public-prefixed vars (`NEXT_PUBLIC_`, `VITE_`, `PUBLIC_`) become `ARG`/`ENV` directives; server env stays in a K8s Secret synced by the control plane (utils.ts:100-113).

Build/push: `generateBuildKitStage` (utils.ts:186-253) writes `~/.docker/config.json` from the `dockerhublogin` credential and runs `buildctl build … --output type=image,name=$DOCKER_IMAGE_VERSION,push=true --output …LATEST,push=true --export-cache/--import-cache type=registry,ref=hav0ky/${appName}-cache:buildcache`, extracting the digest into `image-digest.txt`. Tags are `hav0ky/${name}-app:${BUILD_NUMBER}` and `:latest` (nextjs.ts:115-116).

Status writeback has three racing writers, all funnelling into `AppOperationFinalizer.finalizeBuildOperation` (app-operation-finalizer.ts:160): (1) the pipeline `post { success | failure }` block curls `/api/webhooks/platform-apps/deployment-record` with a global shared secret (nextjs.ts:365-479); (2) `BuildPollingService`, an in-process `setTimeout` loop (build-polling.ts:398-414) that polls Jenkins every 10s for 30min, then does a 60s K8s health check before finalizing; (3) `POST /recover-build` (recover-build/route.ts:101). `Platform_App_Deployments.complete_build` (queries.ts:3626-3644) is a compare-and-set `UPDATE … WHERE status IN (allowed)`, so the loser sees `updated:false` and returns early.

Git webhooks (github/gitlab/bitbucket routes) verify per-app secrets, then `queueBuild` onto BullMQ; `build-worker.ts:37` invokes `AutoDeployService.deploy`, which refreshes the OAuth token, rewrites the job XML, and triggers.

**Worth keeping in v2:**

- **Full pipeline regeneration on every deploy instead of mutating an existing job** — `updateJobConfig` regenerates the complete definition from current DB state before every redeploy and auto-deploy, so job config can never drift from the app record. Whatever replaces Jenkins should keep this 'the build definition is derived, never edited' property. (`C:/cloud-services/lib/services/jenkins.ts`)
- **DB-backed per-app mutation lock + idempotency keys + queue-level delivery dedupe** — Three independent layers stop duplicate/concurrent builds: `acquireAppMutationLock` (resource-mutation-lock.service.ts:181-241) refuses when another op is in flight, `findByIdempotencyKey`/`createIdempotent` (app-release-build.service.ts:130-138, 188-205) collapse retries, and `queueBuild` uses `delivery-${deliveryId}` as the BullMQ jobId (build-job.ts:19-21) so GitHub re-deliveries are free. This is the most mature part of the subsystem. (`C:/cloud-services/lib/app-operations/application/resource-mutation-lock.service.ts`)
- **Compare-and-set finalization (`complete_build`) with an allowed-current-status guard** — `.update(...).eq('app_id',...).eq('build_number',...).in('status', allowed_current_statuses)` is an atomic CAS; the losing writer gets `updated:false` and the finalizer short-circuits (app-operation-finalizer.ts:213-232). With three racing writers this is the only reason status writeback isn't corrupt. Keep the pattern, cut the number of writers. (`C:/cloud-services/lib/supabase/queries.ts`)
- **Ephemeral GIT_AUTH_URL passed as a build parameter instead of baking the OAuth token into the job config** — jenkins.ts:69-94 injects a PasswordParameterDefinition and rewrites the clone to `${GIT_AUTH_URL:-<clean url>}`, while the persisted XML only ever contains the credential-stripped URL (`sanitizeGitUrl`, jenkins.ts:54-60). The instinct — short-lived credential at trigger time, never at rest in the job definition — is exactly right for v2. (`C:/cloud-services/lib/services/jenkins.ts`)
- **Public-prefix build args vs runtime K8s Secret split** — Only `NEXT_PUBLIC_*` / `VITE_*` / `PUBLIC_*` become Docker build args; everything else is deliberately kept out of image layers and injected at runtime via a Secret (`generateEnvSecret` returns `secretYaml: ''`, `createInPipeline: false` — utils.ts:100-113). This is the correct security boundary and matches Vercel's model. (`C:/cloud-services/lib/jenkins/pipelines/utils.ts`)
- **Repo Dockerfile wins, otherwise generate one with in-build runtime detection** — `if [ -f Dockerfile ]` → build as-is; else generate from a per-framework template after detecting Node/Python/Java version and package manager inside the build container where the repo actually exists (dockerfiles/index.ts:28-165, 891-922). Doing detection in the build rather than in TypeScript is right, and the generated Dockerfiles are multi-stage, non-root, and use `--chown` correctly. (`C:/cloud-services/lib/jenkins/dockerfiles/index.ts`)
- **BuildKit with registry cache import/export and a metadata-file digest** — `buildctl build --export-cache/--import-cache type=registry,ref=…-cache:buildcache,mode=max` plus `--metadata-file buildkit-meta.json` → `image-digest.txt` gives cross-build layer caching and a content-addressed digest for the release record. Correct primitives; they just need a real registry and per-tenant isolation. (`C:/cloud-services/lib/jenkins/pipelines/utils.ts`)
- **Ingress apply that preserves custom-domain rules across redeploys** — `generateSmartIngressApplyScript` (utils.ts:274-298) snapshots non-platform hosts/TLS entries with jq before `kubectl apply` and re-attaches them afterwards, solving the real bug where last-applied-configuration wipes customer domains. The behaviour must survive into v2 even if the mechanism (shell + jq) doesn't. (`C:/cloud-services/lib/jenkins/pipelines/utils.ts`)
- **Section-allowlist build log sanitiser** — `VISIBLE_STAGES` (jenkins.ts:767-783) plus `parseSections`/`sanitizeRawBuildLogs` (jenkins.ts:932-1010) drop entire stages the customer shouldn't see rather than trying to redact line by line. Allowlisting sections is the right shape; the 90-entry `LINE_BLOCK_PATTERNS` bolted on top is not. (`C:/cloud-services/lib/services/jenkins.ts`)
- **Per-app git webhook secrets with timing-safe verification and multi-app secret matching** — github/route.ts:113-137 iterates candidate apps for the same repo and picks the one whose secret validates the HMAC, so several apps can share a repo without weakening auth; `validateSignature` length-checks before `timingSafeEqual` (lib/webhooks/github.ts:32-37). Contrast this with the single global Jenkins webhook secret, which is the thing to throw away. (`C:/cloud-services/app/api/webhooks/git/github/route.ts`)

**Drop:**

- Jenkins entirely — job-per-app config.xml generated by TypeScript string interpolation. The whole class of injection, escaping and XML-wellformedness bugs above exists only because build definitions are text documents assembled from user input at request time.
- The 14 near-duplicate pipeline templates (~6,700 lines). nextjs/nodejs/express/python/java/vue/vite-react/angular/sveltekit/nuxtjs/generic-docker differ by a handful of lines each; every fix has to be applied eleven times, which is exactly why the image-scan misconfiguration and the unquoted branch are uniform across all of them.
- `hardenPipelineXml` and `injectBuildRetentionOptions` — post-hoc regex and substring surgery on a document you just generated. If the generator needs patching afterwards, the generator is wrong; and the patch silently no-ops on inputs it doesn't recognise.
- The global `JENKINS_DEPLOYMENT_RECORD_SECRET` shared-secret webhook. One static secret, present in plaintext in every tenant's build environment, authorising status writes for every app in the platform.
- Cluster-admin `kubeconfig_file` bound into every application build pipeline's environment block. Builds must never hold cluster credentials; deployment is a separate, privileged step.
- The shared `hav0ky` Docker Hub namespace and the single `dockerhublogin` credential. No tenant isolation at the registry, and the mutable `:latest` tag as a deployment source (resize.ts:82 `DOCKER_IMAGE_LATEST`) instead of an immutable digest.
- The in-process `setTimeout` build poller (`BuildPollingService`) and the `/recover-build` endpoint that exists to paper over it.
- Jenkins as the source of truth for build history (deployments/route.ts N+1 fan-out). The database should own release history end to end.
- The dead `Create Environment Secret` stage and the `secretYaml` / `createInPipeline` plumbing that is hardwired to empty/false in every pipeline.
- `<hudson.triggers.SCMTrigger><spec>H/1 * * * *</spec>` in generated jobs — an unmanaged trigger that is either dead config or an unaudited deploy path.
- The `simple-test` framework option. It is a Jenkins smoke test exposed as a customer-selectable framework, it is the one template with a live SCM trigger and a Groovy-literal injection, and its jobs are incompatible with the parameterised trigger every code path uses.
- `build_command` and `output_directory` as v1 shaped them — either implement them properly in v2 or remove them from the API and UI; do not keep collecting and displaying settings the builder ignores.
- The four-tier `PLATFORM_APP_RETENTION_POLICIES` table until something actually resolves a plan per app.
- The ~90-entry `LINE_BLOCK_PATTERNS` regex log filter plus the second `sanitizeBuildLogs` pass in the API route. Two independent redaction layers, both pattern-based, both guessing at what Jenkins/Kaniko/BuildKit will print. Emit structured build events instead of scraping console text.
- Jenkins Blue Ocean stage-log fetching with a filtered-full-log fallback (jenkins.ts:625-719) — two code paths producing different output for the same request.

**v2 requirements:**

- Build definitions must be data, not generated text. The builder receives a typed job spec (repo, ref, framework, resource class, build args) over an API; no user value is ever concatenated into a shell command, a Groovy script, or an XML document. If a shell command is unavoidable, use argv arrays — never a string.
- Validate every field that reaches the build at the API boundary, with the same strictness on create and update. `branch` needs a git-refname allowlist (`^[A-Za-z0-9._/-]{1,255}$`, no leading/trailing slash, no `..`, no leading `-`). `repository_url` needs host + path allowlisting, not `z.string().url()`. App rename must run the identical validator and transform as app create.
- Builds must be untrusted-code execution and isolated accordingly: no cluster credentials, no registry write credentials for other tenants, no platform secrets in the build environment; per-tenant network egress policy; rootless/isolated builder (BuildKit with a per-tenant worker or Firecracker/gVisor sandbox); a hard CPU/memory/time budget.
- Exactly one writer for build status, on a durable substrate. A persisted job/lease model (BullMQ jobs, or a `build_runs` table with a worker lease and heartbeat) that survives control-plane restarts — no `setTimeout` chains, no manual recover endpoint. Reconciliation must be a scheduled sweep, not a user-facing button.
- Build outcome must be reported by the platform's own trusted observation, not by the build job. The runner reports progress; the control plane decides success from the actual rollout state (ready replicas at the expected image digest) before marking a release live or starting billing.
- Rollout must gate the release. A `kubectl rollout status` timeout (or its v2 equivalent) fails the deploy, keeps the previous revision serving, and never activates billing. Health must be verified against the app's configured healthcheck path, not just a TCP port — v1's `generateProbeYaml` deliberately ignores `healthcheckPath` (utils.ts:56).
- Per-tenant registry isolation with immutable, digest-pinned releases. One repository (and ideally one robot credential) per app, releases addressed by `repo@sha256:...`, and rollback restricted to digests the platform itself recorded for that app — never an image reference supplied over a webhook.
- Machine-to-machine auth between runner and control plane must be per-run and short-lived (signed run token or mTLS scoped to one build of one app), replacing the global shared secret. Every status write must be authorised against the app the token was issued for.
- One build recipe engine, not fourteen templates. Framework detection and Dockerfile generation belong in a single versioned builder image with a declarative per-framework manifest, so a security or correctness fix lands once.
- Honour the build configuration the product advertises: custom build command, install command, output directory, root directory (monorepos), and node/python/java version pinning — or remove those fields. Implement them as builder inputs, never as shell interpolation.
- Security gates must be explicitly configured and enforced, with the policy visible to the customer: which scanners run, which severities block, and how to request an exception. No defaults that silently evaluate to 'never block'.
- Structured build telemetry instead of log scraping: the builder emits typed step/stage events with timestamps and outcomes; raw logs are stored separately with secret redaction done at emit time by the component that knows what is secret. The UI renders events, not filtered console text.
- The database is the sole source of truth for releases and history. The build system is queried only for live log tailing of an in-flight run.
- Every deploy trigger goes through one authorised path: no builder-side SCM polling, no out-of-band triggers, and every run must have a pre-created release record before the build starts so status writeback can never find 'record not found'.
- Concurrency, idempotency and locking must be carried forward as first-class: per-app mutation lock, idempotency key on every trigger, delivery-id dedupe on webhooks, and compare-and-set finalization — v1 got these right and they should be requirements, not incidental.
- Test the generator. Golden-file tests for every produced build spec, property tests that hostile branch/URL/app-name/env-value inputs never escape their parameter, and an integration test that a failed rollout produces a failed release and no billing activation.

### Kubernetes runtime (v1 platform-apps PaaS): manifest generation, probes, sizing, rollback, resize, status reconciliation, tenant isolation, delete/orphans

Every app is one flat set of objects in the single `default` namespace. Given the DB column `platform_apps.name` = N, the pipeline generators derive: Deployment `{N}-app` (nextjs.ts:238-271), Service `{N}-service` ClusterIP 80→containerPort (nextjs.ts:276-288), cert-manager Certificate `{N}-cert` → secret `{N}-tls` via ClusterIssuer `letsencrypt-prod` (nextjs.ts:293-305), Ingress `{N}-ingress` with one rule for `{N}.{APP_DOMAIN}` (nextjs.ts:309-333), plus Secret `{N}-env-secret` written by the control plane, not Jenkins (utils.ts:104, kubernetes-info.ts:287). Pod label/selector/container-name are all `app={N}-app`; image is `hav0ky/{N}-app:{BUILD_NUMBER}` with `imagePullPolicy: Always` and no `imagePullSecrets`. Outside K8s: Cloudflare A record `{N}.{domain}`→`KUBE_IP` (deployment.ts:162), Jenkins jobs `{N}-job`/`{N}-resize-job`/`{N}-delete-job`, Docker Hub repos `hav0ky/{N}-app` and `hav0ky/{N}-app-cache` (utils.ts:240).

Tiers live in `APP_SIZE_SPECS` (utils.ts:27-33): small 250m/500m·256Mi/512Mi·1, medium 500m/1·512Mi/1Gi·2, large 1/2·1Gi/2Gi·3, xlarge 2/4·2Gi/4Gi·4, xxlarge 4/8·4Gi/8Gi·6. nextjs/java/nuxtjs/generic-docker floor at `medium`; the rest and resize.ts:38 do not.

Probes are always `tcpSocket` on the container port — readiness 15s/5s/3s/6, liveness 30s/10s/5s/3 (utils.ts:63-85). `healthcheck_path` is explicitly accepted and discarded ("The healthcheckPath parameter is accepted but ignored here", utils.ts:55). Its only real uses are an on-demand HTTPS fetch from the control plane (check-health-path/route.ts:63) and a log-only post-deploy check (build-polling.ts:693).

Rollback never uses `kubectl rollout undo`. It picks a target from the last 20 successful manual/webhook rows in `platform_app_deployments` (queries.ts:3443-3451), builds `repo:tag@digest` (image-ref.ts:17-32), does an anonymous Docker Hub HEAD preflight (container-registry.adapter.ts:9-28), then issues one JSON Patch replacing `/spec/template/spec/containers/0/image` (kubernetes-info.ts:248-267). It depends entirely on the DB row, the Docker Hub tag still existing, and the container being index 0. Env vars and replicas are not rolled back.

Resize regenerates a whole `{N}-resize-job` pipeline (jenkins.ts:1147-1178), syncs the env Secret, and applies a fresh Deployment manifest built from `:latest` (resize.ts:114-115), then verifies by inferring the tier from replica count (build-polling.ts:63-75).

Reconciliation is `AppStatusService.syncStatus` (app-status.ts:113-259), called only from user-facing reads (health/route.ts:59, platform-app-service.ts:637). `pending`/`stopped`/`deleting`/`building` are skipped; otherwise `readyReplicas > 0` ⇒ running else failed, with a 120s grace window from an in-memory map plus `updated_at` (app-status.ts:192-211). The `unreachable` guard at app-status.ts:171 can never fire, because both K8s calls swallow their own errors and return null (kubernetes-info.ts:767-771, 805-809).

Delete deletes the DB row first (deployment.ts:349-355), then fires DNS delete, Jenkins job deletes, and a `{N}-delete-job` that removes Deployment/Service/Ingress/Certificate/`{N}-tls` — and a secret named `{N}-app-env-secret`, which never existed.

**v2 requirements:**

- One Kubernetes namespace per app (or per project), created and labelled by the control plane, carrying a default-deny NetworkPolicy (egress allowed only to DNS, the ingress controller and the public internet — never to the API server, kubelet, or sibling namespaces), a ResourceQuota and LimitRange matching the paid tier, and `pod-security.kubernetes.io/enforce: restricted`. Namespace deletion must be the single teardown primitive.
- A hardened pod spec as a non-negotiable template: `runAsNonRoot`, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem` where possible, dropped capabilities, `seccompProfile: RuntimeDefault`, a dedicated ServiceAccount with `automountServiceAccountToken: false`, and an explicit decision on gVisor/Kata for untrusted customer code.
- Kubernetes object names derived from an immutable, server-generated identifier (the app UUID or slug), never from a user-chosen display name — plus a database UNIQUE constraint and a transactional claim so a name can never be double-allocated, and so renaming an app never renames infrastructure.
- Replace pipeline-generated YAML with typed manifest construction in the control plane, applied via server-side apply with a stable field manager. One code path for deploy, resize and rollback; the manifest must be renderable and diffable in tests without running Jenkins.
- HTTP probes driven by the stored healthcheck path, with a startupProbe covering slow boots, a readiness probe that actually gates Service endpoints, and a liveness probe with a conservative failureThreshold. Fall back to TCP only when the customer configures no path, and surface probe configuration in the UI as what it really is.
- Rollout-aware operations: every deploy, resize and rollback must watch the Deployment to Available (or observedGeneration + updatedReplicas + readyReplicas convergence) with a deadline, roll back automatically on failure, and only then record success and repoint the active release. `progressDeadlineSeconds` must be set on every Deployment.
- Immutable, digest-pinned releases with a durable revision record capturing image digest, env-var snapshot, resource tier and replica count. Rollback restores that whole revision — not just the image — and any later resize preserves the pinned digest.
- A private, per-tenant container registry (or per-tenant repositories with scoped pull credentials and per-namespace imagePullSecrets), plus a retention policy that guarantees every image referenced by a rollback-eligible revision still exists.
- A single authoritative tier table used by pricing, manifest generation, quota, and verification, with per-framework minimums applied uniformly across deploy and resize. Verification must compare actual requests/limits/replicas, not infer the tier from replica count.
- A continuous background reconciler (a controller or a scheduled sweep) that is the only writer of runtime status, distinguishes 'Kubernetes unreachable' from 'app unhealthy' with an explicit, tested branch, and never marks apps failed during a control-plane outage. Grace/debounce state must be durable, not a process-local Map.
- Least-privilege Kubernetes credentials: a namespaced, RBAC-scoped ServiceAccount for read paths that serve tenant dashboards, separate from the privileged credential used for provisioning; no single cluster-wide kubeconfig shared by both.
- Transactional teardown with a durable deletion record: mark the app deleting, tear down infrastructure, verify, and only then remove the row. Any residue must land in a reconcilable orphan queue rather than a warning string, and cleanup must cover DNS (paginated), registry repositories and build caches, CI jobs and every Secret by its real name.
- Per-app observability keyed by label selectors and namespace, never by pod-name prefix. Pod-level events, restart reasons, previous-container logs and OOM/scheduling diagnoses must reach the customer-facing UI, not only the admin monitor.
- Real test coverage of the runtime layer against the real implementations: golden-file assertions on generated manifests, and simulated API-outage / crash-loop / unpullable-image scenarios asserting the resulting status transitions. No production service may be 'covered' by a stub that reimplements a different API.
- Ingress-layer defaults the platform owns rather than the customer: per-app rate limits, body-size limits, timeouts and HSTS applied declaratively and preserved across redeploys, with TLS readiness gating the app's advertised go-live so no app is announced while serving a default self-signed certificate.

### Networking, DNS, TLS and Domains (v1 platform-apps PaaS)

DEFAULT HOSTNAME. An app's name is its hostname. `config/domain.ts:7` sets `APP_DOMAIN = process.env.APP_DOMAIN || 'galaxyhvh.com'` (live value is `ahurasense.com`, `.env:70`); `getAppDomain()` (`config/domain.ts:21-23`) returns `<name>.<APP_DOMAIN>`. During create, `lib/services/deployment.ts:159-162` hard-requires `KUBE_IP` and calls `DNSService.createRecord(config.name, process.env.KUBE_IP)`. `lib/services/dns.ts:31-38` creates one Cloudflare **A** record: `type:"A", name: appName, content: ipAddress, proxied: false, ttl: 300` in `CLOUDFLARE_ZONE_ID`. Cloudflare is used ONLY as an authoritative DNS host — `proxied:false` means no CDN, no WAF, no DDoS scrubbing, no anycast. Name collisions are guarded only by `check_name_exists` (`lib/services/platform-app-service.ts:365`, implementation `lib/supabase/queries/platform_apps.ts:61-78`, which returns `false` on DB error — fails open) plus a pre-create Cloudflare `recordExists` probe (`dns.ts:89-104`). I confirmed against the live DB that `platform_apps` has a unique index only on `slug`, never on `name`.

KUBE_IP. `.env:87` `KUBE_IP=157.245.101.209` — one IP, the single host-network ingress-nginx node. It is written verbatim as the A-record `content` (`dns.ts:35`), as the apex A answer for custom domains (`dns-provider.adapter.ts:64-67`), stored on each app row (`deployment.ts:132`), and used as the expected-IP set for routing checks (`dns-routing.adapter.ts:111-115`, `domain-service.ts:1264-1269`). The read paths `.split(",")`; the write paths do not.

CUSTOM DOMAINS. `DomainService.addDomain` (`domain-service.ts:117-224`) mints `verify_<8 random bytes>` and creates a pending row — unless `resolveOwnershipMode` (`:1195-1243`) decides the domain is "platform managed", in which case it calls `markVerified` immediately with no DNS proof. Otherwise `verifyDomain` (`:227-317`) resolves TXT at `ahuracloud-verify.<domain>` (`config/domain.ts:14`) through a fixed resolver list `1.1.1.1, 8.8.8.8` (`dns-provider.adapter.ts:22,265-278`) and substring-matches the token (`:251`).

The default hostname gets its own separate cert from the deploy pipeline: `metadata.name: <name>-cert`, `secretName: <name>-tls`, issuer hardcoded `letsencrypt-prod` (`lib/jenkins/pipelines/nextjs.ts:291-320`). SSL confirmation is a chain-less `tls.connect` probe (`tls-ssl-probe.adapter.ts:169-215`) checked for a Let's Encrypt issuer + SAN match (`domain-service.ts:676-690`).

BANDWIDTH. `refreshCurrentUsage` (`platform-app-bandwidth.ts:137-212`) reads `container_network_receive/transmit_bytes_total{pod=~"<app>-app.*"}` (`prometheus.ts:263-308`), diffs against saved per-pod counters (`utils.ts:240-272`), accumulates into a monthly row, and may charge overage. **v2 requirements:**

- Hostname allocation must be decoupled from the user-visible app name: allocate an immutable, non-guessable deployment hostname (e.g. <app-slug>-<random>.<APP_DOMAIN>) at create time, and treat display names as free-form mutable metadata that touches nothing in DNS, Kubernetes or CI. Back it with a DB unique constraint on whatever field the hostname derives from — v1 has one on slug only, not on name.
- Domain ownership must be proven per-user, always. No registrar-account membership may substitute for a DNS proof unless the requesting user is the recorded owner of that exact zone in the platform's own records. Verification should require the token as an exact TXT value, resolved from at least two independent vantage points, with a public-suffix-list-aware notion of apex.
- One wildcard certificate for the platform subdomain space (*.<APP_DOMAIN>, DNS-01) serving all default hostnames, plus per-domain certificates only for customer-attached domains. Track ACME issuance budget explicitly and expose remaining headroom, so growth is never silently capped by a rate limit discovered in production.
- Traffic must arrive through an edge that provides CDN caching, TLS termination, a managed WAF and DDoS absorption, fronting at least two ingress origins. v1 has exactly one origin IP (KUBE_IP=157.245.101.209) behind unproxied A records; anything less than multi-origin with health-checked failover is not an enterprise bar.
- Ingress and certificate state must be reconciled declaratively by a controller reading desired state from the database, not imperatively mutated by generated shell inside CI jobs. Every domain attach/detach must be idempotent, retryable, and incapable of destroying unrelated hosts on the same object even under partial failure.
- Long-running domain operations must run on a durable queue with at-least-once delivery, bounded retries and dead-lettering — not `after()` plus a floating promise. Operation state must converge without depending on a user polling an endpoint.
- Bandwidth must be metered at the HTTP edge (request/response bytes attributed to a specific hostname/route), never from pod NIC counters, so intra-cluster, database and object-storage traffic is not billed as customer web bandwidth.
- Metering, quota enforcement and overage billing must run on an owned, monitored schedule with alerting on missed runs. No billing side effect may ever be triggered by a customer-facing GET; separate 'read usage' from 'advance the meter'.
- Per-tenant network isolation: one namespace per tenant (or equivalent), default-deny NetworkPolicies, and TLS private keys stored where no other tenant's workload shares a namespace with them. v1 puts every app and every tenant TLS secret in `default` with no NetworkPolicy anywhere in the repo.
- Every server-side outbound fetch derived from user input (health checks, webhooks, previews) must run through an SSRF guard: scheme allowlist, DNS-resolution-time private/link-local/metadata blocking, redirect capping, and no leaking of status codes for blocked targets.
- Quota limits (domains per app, apps per user, request-body size) must be enforced in the service layer so every entry point — dashboard, public API, internal tooling — is bound by the same rule.
- Zone-provider access must be paginated, filtered and scoped: look records up by name rather than listing the zone, and never enumerate the whole shared registrar account on a per-user request path.
- The platform must be able to repoint every hostname when an ingress IP changes — a bulk, resumable re-targeting operation, or (better) an architecture where customer records point at a stable edge name rather than a raw origin IP.
- If v2 keeps a 'redirect to primary domain' feature, it must produce an actual 301 at the edge for non-primary hostnames, with the DB flag and the running configuration reconciled.

SCHEMA (verified against the live prod DB, project xafjjpgazdxhktpfeuri, not against the repo). ### Platform-apps PaaS: API surface, authentication, authorization and multi-tenancy (app/api/services/platform-apps/**, app/api/v1/apps/**, app/api/webhooks/**)

There are two disjoint API surfaces. The INTERNAL surface is 37 routes under app/api/services/platform-apps/**. 29 of them authenticate with `authenticateUser()` (lib/auth/server-auth.ts:11-35), which is cookie-session ONLY — it calls `supabase.auth.getUser()` with no header fallback, so a PAT can never reach these routes. 8 integrations routes instead inline `createSSRClient().auth.getUser()`. One route (cleanup-logs) uses a shared CRON_SECRET bearer (lib/security/cron-auth.ts:13-22, fails closed). One (prices) has no auth at all.

The PUBLIC surface is 5 routes under app/api/v1/apps/**, all wrapped in `withV1Auth` (lib/api/v1-middleware.ts:26-70), which calls `authenticateApiRequest` (lib/api-auth.ts:32-120). That accepts either a `sk_`-prefixed PAT (SHA-256 lookup, timing-safe compare, expiry check — lib/supabase/queries/api_keys.ts:156-212) or a Supabase JWT. PATs carry NO scopes: a key is full account authority. Session callers are hardcoded to plan "free" (lib/api-auth.ts:101-103, `// TODO: Lookup user's plan`), so rate tiers only vary for PATs.

Authorization is entirely hand-rolled per route. That check is present and correctly ordered (fetch → compare → mutate) on 34 of 37 internal routes and all 5 v1 routes. It is missing entirely on integrations/linked (both branches), and update-project checks the app but never the target project.

- Authorization must be structural, not per-route. Every route is declared through one wrapper that resolves the target resource, loads it WITH the caller's tenant scope applied, and hands the handler an already-authorized object. It must be impossible to write a handler that receives a raw app_id from the request body — integrations/linked and update-project prove that reviewers cannot be relied on to spot the omission.
- Infrastructure addressing by immutable identifier. Deployments, Jenkins/build jobs, secrets, ingresses and DNS records derive from a server-generated, never-updatable id (or a name that is DB-unique AND immutable after create). Display names are a separate, freely editable, purely cosmetic column that no downstream system ever reads.
- Hard tenant isolation in the cluster: one namespace per tenant (or per app), with default-deny NetworkPolicy, ResourceQuota, and RBAC that cannot address another tenant's objects even if the control plane is tricked into asking. A single fumbled ownership check must not equal cross-tenant compute takeover.
- No shell or template-string code generation for builds. Build definitions must be data (structured build spec -> containerized builder with argv arrays), never strings interpolated into Groovy or sh. If any string interpolation into an executable context survives, it must go through a single mandatory encoder.
- One update path per resource with an explicit, allow-listed field set, and separate schemas for user-writable versus system-writable fields. status, deployment_url, image references and port must be writable only by the platform's own reconciler, never by a request body.
- Real RLS as a second line of defense: application code runs as the requesting user, service-role usage is confined to a small audited set of system operations, and the RLS policies are covered by tests that actually exercise a foreign tenant's id.
- Scoped, revocable API credentials: per-key scopes (apps:read, apps:deploy, apps:env:read...), a revoked state distinct from deletion, last-used and created-by metadata, and an authorization decision derived from the scope — not merely a rate-limit prefix.
- Rate limiting applied by the framework with a declared cost per operation, so a new route cannot ship without one. Secret-reading operations get their own stricter budget.
- Persistent, queryable, tenant-visible audit for every secret read, export, deploy, rollback, resize, delete and integration change — written to durable storage, with server-generated request ids and a trusted-proxy-derived client IP. A customer must be able to answer 'who read my environment variables and when'.
- Egress control for any server-initiated fetch derived from customer data (health checks, webhooks, custom domains): scheme allow-list, DNS resolution pinned and re-checked after redirects, RFC1918/link-local/metadata ranges denied, redirects capped or disabled.
- Per-app, rotatable credentials for build-agent -> control-plane callbacks, bound to the specific operation being reported. No global secret may ever be placed in an environment a customer's own build code can read.
- One canonical env-var service used by both the public API and the dashboard, with identical rate limits, identical audit, and values never returned in bulk or echoed back in mutation responses.
- Uniqueness and concurrency enforced by the database (unique constraints, transactional create), not by check-then-act reads that fail open.
- A public API that is complete and is the same code path as the dashboard — v1 today has no create endpoint and diverges from the internal surface on secret handling, which is how the export rate limit ends up bypassable.

Neither table appears in supabase/migrations/ or supabase/schema.sql — they were created out of band. ## Research tracks (with independent verification)

### vercel-enterprise

Vercel is four products stacked behind one git push; the enterprise tier is mostly governance bolted onto that core.

DEPLOY MODEL. Every push to a connected repo (GitHub/GitLab/Bitbucket/Azure DevOps) produces a deployment with a permanent immutable URL; branches and PRs get preview URLs automatically. Production is an *alias*, not a build — promoting a preview or rolling back is a pointer swap with no rebuild. Production deployments sit in Staged → Promoted → Current states and can be gated by Deployment Checks (GitHub Actions results) before aliasing; Force Promote bypasses. Rolling Releases (Pro/Enterprise) shift traffic in configurable stages with cookie-based bucketing (`_vcrr_<hash>`), comparing Speed Insights between canary and base. Skew Protection pins a client's API calls to the deployment that served its HTML. Deployment Protection gates preview and/or production URLs behind Vercel auth, password, Trusted IPs (Enterprise) or the customer's own IdP (Passport, Enterprise); Pro pays $150/mo for the "Advanced" bundle.

BUILD. Isolated per-build containers (Hobby/Pro 8 GB RAM / 32 GB disk / 2–4 vCPU; Enterprise custom and queue-free), 45-min timeout, 1 GB build cache retained one month, framework auto-detection, monorepo skip-unaffected (does not consume a concurrency slot), Turborepo/Nx remote caching, branch-based queue dedupe (newest commit wins), on-demand extra concurrency.

RUNTIME. Fluid compute — instances serve concurrent requests and scale to zero; Node/Python/Go/Ruby; streaming; regional pinning with automatic failover; Enterprise concurrency scaling to 100,000. ISR is the crown jewel: build-time route-cacheability metadata pushed to every region, durable per-deployment cache (31 days), request collapsing, ~300 ms globally consistent purge, atomic HTML+data invalidation, stale-on-failure with 30 s retry, caches survive rollback.

NETWORK. Anycast over ~20 AWS regions, automatic TLS, unlimited domains per project (soft caps 100k Pro / 1M Enterprise), wildcard certs via Vercel nameservers, free platform-wide DDoS mitigation, WAF (custom rules, IP blocking, managed rulesets, attack mode, JA3/JA4 fingerprints).

ENTERPRISE. SAML SSO; SCIM Directory Sync with group→role mapping and `vercel-role-*` lockout escape hatch; unusually granular RBAC — team roles (Owner, Member, Developer, Security, Billing, Pro/Enterprise Viewer, Contributor), project roles (Admin/Developer/Viewer), Access Groups, and composable permission groups (Create Project, Full Production Deployment, Env Var Manager, Deployment Protection Manager); owner-only audit logs with CSV export and Audit Log Drains to S3/Splunk/Datadog/Panther (replacing the older Custom SIEM streaming); Drains for logs/OTEL traces/analytics at $0.50/GB; Secure Compute — dedicated VPC, static egress IP pair, AWS VPC peering (50 peers, 100 projects/network), active/passive region failover, $0.15/GB private egress, Edge runtime explicitly excluded; SOC 2 Type 2, ISO 27001:2022, PCI SAQ-D/A, HIPAA BAA, GDPR + EU-US DPF, TISAX AL2; 99.99% SLA with 10/25/50% credits; spend limits with 50/75/100% alerts, webhooks, optional auto-pause (polled every few minutes — not a hard cap).

DX. A very large CLI (deploy, build, dev, env pull, promote, rollback, bisect, logs, curl, httpstat, traces, metrics, firewall, rolling-release, cache purge, redeploy, target). Preview comments are free on every plan via the Toolbar, with Slack threading and email notification. Deployment summaries list middleware matchers, static assets and functions with sizes/regions. Env vars scope per environment with per-branch overrides, 64 KB total budget, auto-redaction of 32+ char values in build logs.

The strategic change for competitors: Next.js 16.2 (March 2026) shipped a stable public Deployment Adapter API plus a public compatibility test suite, and Vercel's own adapter uses it with no private hooks. Framework fidelity is now an engineering problem, not reverse engineering.

**Recommendation:** PICK: **Knative Serving on Kubernetes 1.34+, fronted by Envoy Gateway (Gateway API), built by BuildKit + Paketo Buildpacks, images in self-hosted Harbor, orchestrated by a Postgres-backed reconciler in the existing Next.js control plane, with a first-party Next.js Deployment Adapter, Ory Polis for SAML/SCIM, and gVisor RuntimeClass for tenant isolation.**

Why this and not the alternatives: Vercel's hardest semantics — an immutable deployment that gets a permanent URL, promotion as an alias swap with no rebuild, instant rollback, percentage-based rolling releases, and per-preview URLs — are *exactly* Knative Serving's Revisions, tags and traffic percentages. You get the product's core primitive from a CNCF graduated project instead of writing a revision engine. Scale-to-zero is not a nice-to-have here; it is the unit economics of a PaaS whose customer apps are idle 95% of the time. That single alignment is worth the extra control plane, and it is the difference between "5 engineers ship this in 2026" and "5 engineers build a scheduler for 2 years".

Components, named, with the recent status changes that force the choice:
- **Edge: Envoy Gateway v1.9 (released 14 Aug 2026), Gateway API.** This is not optional. `kubernetes/ingress-nginx` was retired 31 March 2026 with no further security patches; the Kubernetes Steering and Security Response Committees state that staying on it "leaves you and your users vulnerable to attack". v1's host-network ingress-nginx DaemonSet is now unpatched software in the request path of a commercial product. Use `ingress2gateway` (1.0, March 2026) to convert. Terminate customer TLS here, not in Knative — `net-gateway-api` is still Beta and its HTTP-01 path is capped at 64 certificates by the Gateway API spec.
- **Builds: BuildKit (rootless) on a dedicated, tainted node pool + Cloud Native Buildpacks (Paketo) for zero-config, Dockerfile as escape hatch.** Kaniko was archived by Google on 3 June 2025 (all maintainers retired); do not adopt it. Nixpacks is in maintenance mode with Railway pointing to Railpack, so do not bet the build layer on either — Paketo is the CNCF-governed option. Registry-backed layer cache gives you Vercel's 1 GB/one-month build cache behaviour.
- **Registry: Harbor (CNCF graduated), self-hosted.** Docker Hub namespace `hav0ky` must go: it is a shared public namespace with pull rate limits sitting in your production path, and it is a sovereignty embarrassment. Harbor also gives you Trivy scanning and image signing you will need for SOC 2 evidence.
- **Orchestration: delete Jenkins.** Replace it with a level-triggered reconciler: the Next.js app writes desired state (app, deployment, alias, domain, env) into Supabase Postgres; a small Node/Go reconciler loop continuously drives Kubernetes to match, with a Postgres-backed durable queue (Graphile Worker or pg-boss) for the build steps. Do **not** reach for Temporal at this team size — it is the right answer at 30 engineers and a self-hosted liability at 5. Jenkins-on-Kubernetes is edge-triggered and stateful in the worst way: a lost webhook is a permanently wrong cluster. A reconciler is self-healing and is also how you kill the branch/name injection RCE — desired state becomes typed rows, never shell-interpolated strings.
- **Framework fidelity: write an AhuraCloud Next.js Adapter against the stable Adapter API (Next.js 16.2+, current 16.3.3) and run the public compatibility test suite in CI.** This is the single highest-leverage item on the whole list and it did not exist 12 months ago. It converts "does Next.js really work on your platform?" from a sales objection into a green test badge. Open-source it and pursue verified-adapter status under the `nextjs` GitHub org — free credibility no competitor in India has. Back it with a shared cache handler (`cacheHandler` + `cacheHandlers`) on Redis/Valkey so ISR tag propagation works across replicas, which the Next.js docs list as "Shared Cache Recommended" for functional fidelity on ISR, PPR and `use cache`.
- **Enterprise identity: Ory Polis (formerly BoxyHQ SAML Jackson), Apache-2.0, self-hosted.** It is purpose-built for the multi-tenant SP shape you need — each customer brings their own Okta/Entra, plus SCIM 2.0 directory sync. Do not build SAML yourself, and do not stand up Keycloak-as-IdP for this; wrong shape and heavier.

### build-systems

The single most important 2026 fact: **a container is not a security boundary for untrusted build code.** Three runC escape CVEs disclosed Nov 2025 (CVE-2025-31133, CVE-2025-52565, CVE-2025-52881 — symlink/bind-mount races yielding root on the host or a kernel panic) settled that argument. Every major platform converged on microVMs: Vercel runs Sandboxes in Firecracker microVMs "on the same infrastructure that powers Vercel's build system"; Northflank runs Kata + Cloud Hypervisor in production. If you want the Vercel Enterprise bar, that is the bar.

BuildKit's own maintainers are explicit that rootless BuildKit is *not* a multi-tenant boundary. In moby/buildkit discussion #5796, AkihiroSuda answers a question about exactly this use case with: rootless buildkitd is "just as secure/insecure as running `buildkitd` as a non-root user on the host" — and points to User Mode Linux or Kata for real isolation. Worse, BuildKit's own rootless docs *discourage* `--oci-worker-no-process-sandbox`, the flag their Kubernetes examples use, because it "allows `ExecOp` containers to `kill` (and potentially `ptrace`...) an arbitrary process in the BuildKit daemon container." A shared long-lived buildkitd is a shared trust domain, full stop.

Builder landscape has shifted hard. **Kaniko is dead** as a foundation: Google archived it June 2025; Chainguard's fork (chainguard-dev/kaniko) is explicit minimal maintenance — "No major feature work is planned," tags only, no published binaries. CERN's benchmark also found Kaniko slowest and most memory-hungry on large images. **Nixpacks is in maintenance mode**; its own authors at Railway replaced it with **Railpack**, which is BuildKit-LLB-native and much leaner — but still 0.x (v0.37.1, 24 Aug 2026) shipping breaking changes in its newest release. **Cloud Native Buildpacks graduated CNCF on 11 Aug 2026** with a Quarkslab/OSTIF security audit, and its `rebase` — patching base-OS CVEs across every app in hours without rebuilding — is a genuinely sellable enterprise/compliance feature. **Dagger is mid-rewrite off BuildKit** ("Project Theseus") — wrong time to bet on it.

Orchestrators: **GitHub Actions self-hosted runners are disqualified** — GitHub's own docs say they "can be persistently compromised by untrusted code in a workflow." Jenkins shipped security advisories in Feb, Mar, Apr, May, Jun (×2) and Aug 2026 — a plugin-CVE treadmill a handful of engineers should not be running. Argo's controller holds broad privileges and had 2026 advisories including artifact-repository credential exposure. Tekton (CNCF incubating since Mar 2026) is the least-bad general CI option but is more machinery than you need. Woodpecker is healthy and actively developed but is a CI server, not a PaaS build plane.

The decisive insight: **a PaaS build is not a CI pipeline.** It is one fixed shape — fetch source, build image, push, deploy. There is no user-authored pipeline DSL, no plugin ecosystem, no multi-branch config. Every general CI system forces you to operate a large privileged control plane and expose a config surface you don't want tenants near. Your v1 already proves the cost: `lib/jenkins/pipelines/*.ts` generates Groovy as strings.

Your v1 has two concrete, exploitable-today flaws worth naming: `lib/jenkins/security/index.ts:38` uses `moby/buildkit:latest` (**not** the `-rootless` variant) in a *shared* "common-agent" pod that also holds a `kubectl` container with cluster-deploy rights; and `lib/jenkins/pipelines/utils.ts` writes Docker Hub push credentials into `~/.docker/config.json` *inside the build container*, with cache at `hav0ky/${appName}-cache:buildcache` — one flat Docker Hub namespace keyed on app name, which is a cross-tenant cache-poisoning vector (cf. moby GHSA-xw73-rw38-6vjc). Zero apps have shipped, so none of this needs migrating — delete it.

**Recommendation:** **Build a custom Kubernetes Job controller that runs one ephemeral rootless BuildKit per build inside a Kata Containers microVM, fed by Dockerfile-first detection with Railpack as the zero-config fallback, pushing to a self-hosted Harbor registry.** Retire Jenkins, Kaniko, Nixpacks and Docker Hub entirely.

**The security-correct way to build untrusted customer code on Kubernetes in 2026, stated plainly:** every build runs in its own single-use microVM with its own kernel (Kata via RuntimeClass, Cloud Hypervisor backend), containing a single-use rootless buildkitd that is destroyed with the VM. No shared build daemon, no build ever touching registry push credentials, no cache shared across tenants, and no long-lived state surviving a build. Containers, gVisor, and rootless-BuildKit-on-shared-nodes are all hardening, not boundaries. BuildKit's maintainer says so directly in discussion #5796; the Nov 2025 runC CVEs proved it; Vercel and Northflank both build on microVMs. If you cannot run microVMs, you cannot honestly claim the Vercel Enterprise bar — say "hardened multi-tenant" instead.

**Why a custom controller, not Tekton/Argo/Woodpecker:** a PaaS build is one fixed shape — fetch, build, push, deploy. It is not a pipeline. Every general CI engine makes you operate a large privileged control plane and exposes a user-authored config surface you specifically do not want tenants near, and each is a CVE stream (Jenkins alone: seven advisory rounds in 2026). Your build state machine already lives in Next.js + Postgres. The Kubernetes Job API supplies retries, timeouts and GC free. Roughly 2–3k lines you fully own beats three upstreams you must track. If the team genuinely won't write a controller, pick **Tekton** — and pick it for Tekton Chains' SLSA provenance, which is worth real money at enterprise tier.

**Five non-negotiables, each fixing a live v1 flaw:**
1. **Push credentials never enter the build sandbox.** v1 writes Docker Hub creds into `~/.docker/config.json` in the build container (`lib/jenkins/pipelines/utils.ts`). v2: buildkitd exports an OCI tarball; a separate, more-trusted step performs the push using a short-lived token scoped to exactly one repo path.
2. **Cache is namespaced per tenant, never shared.** v1's `hav0ky/${appName}-cache:buildcache` is one flat namespace keyed on app name — a cross-tenant cache-poisoning vector (cf. moby GHSA-xw73-rw38-6vjc). Scope every cache ref to `(tenant_id, app_id)`. Only read-only mirrored base images may be shared. The cache-hit-rate win from sharing is not worth an image-integrity breach.
3. **Build secrets only via `RUN --mount=type=secret`** — never ARG or ENV, which persist in layers and `docker history`.
4. **Leave Docker Hub.** A sovereign-cloud product pushing all customer images to a US SaaS under a personal-looking `hav0ky` namespace contradicts the value proposition and adds rate-limit risk. Self-host Harbor (CNCF graduated) with per-tenant projects and robot accounts.
5. **Turn on user namespaces (`hostUsers: false`) too** — free defense-in-depth beneath Kata.

**Be honest about the cost — this is the expensive part.** Kata needs bare metal with `/dev/kvm` or genuine nested virtualization. Your current Linode host almost certainly cannot do this; standard cloud VMs can't. **Verify KVM on your hardware before committing to any of this** — it is the gating question. You also need Kubernetes ≥1.33 (ideally 1.36 for userns GA) and Kata ≥3.12 for the Helm chart, meaning a 1.31→1.36 upgrade across five sequential minors. Realistic budget before the first customer build: roughly one engineer-quarter — ~4–8 weeks for the controller at production quality (log streaming, cancellation, queueing, concurrency limits are all yours to write), 2–4 weeks for Kata plus the build node pool, 1–2 weeks for Harbor, plus the cluster upgrade. Ongoing, this is a permanent part-time infrastructure job, not fire-and-forget.

**Two calls I'd revisit later, not now.** Skip multi-arch until a customer asks: QEMU emulation is 5–10x slower on compute-heavy builds, so when arm64 arrives, add native arm64 build nodes rather than emulating. And if "we patched your base-OS CVE across every app in hours, no rebuild" becomes a compliance or sales requirement, switch the zero-config path from Railpack to **Cloud Native Buildpacks** for its `rebase` capability — CNB graduated CNCF on 11 Aug 2026 with a Quarkslab/OSTIF audit, and that single feature can justify its heavier operational weight. Until then Railpack is the cheaper path, because it shares one build engine with your Dockerfile path — but pin it to an exact version: it is 0.x and shipped breaking changes in its most recent release.

**Do not adopt:** Kaniko (archived by Google Jun 2025; Chainguard fork is patch-only, "no major feature work planned"), Nixpacks (maintenance mode, replaced by its own authors), GitHub Actions self-hosted runners (GitHub's own docs say they can be persistently compromised by untrusted workflow code), or Dagger right now (mid-rewrite off BuildKit). Buildah is the one credible runner-up to BuildKit — CERN found it needs no privileges where BuildKit still wants privileged inside a userns — and it becomes the better pick if microVMs turn out to be impossible on your hardware.

### runtime-orchestration

Three status changes since v1 was designed make this rebuild urgent rather than optional.

**ingress-nginx is retired.** Kubernetes SIG Network announced retirement on 2025-11-11; best-effort maintenance ended March 2026. No further releases, bug fixes, or security patches, ever. The planned successor InGate never matured and was also retired. v1 runs ingress-nginx as an internet-facing host-network DaemonSet — that is now a permanently unpatched component on the edge of the network. Gateway API is the official replacement path.

**Kubernetes v1.31 went EOL 2025-11-11.** Supported versions are now 1.34, 1.35, 1.36 (latest 1.36.2, 2026-06-09). v1 is five minors behind with zero security patches.

**runC container escapes.** CVE-2025-31133, CVE-2025-52565, CVE-2025-52881 (disclosed Nov 2025) allow full escape to root on the host via bind-mount/symlink races, including LSM bypass. v1 runs every tenant in the shared `default` namespace with no NetworkPolicy and no ResourceQuota, on stock runC. The only reason this has not been exploited is that the tables are empty.

The counterweight is genuinely good news: **user namespaces reached GA in Kubernetes 1.36** (2026-04-23). Setting `hostUsers: false` maps container UID 0 to an unprivileged host UID, and directly mitigates exactly the CVE class above. It is free, needs no new component, and requires only containerd 2.0+ and a modern kernel. This is the highest leverage single change available.

On autoscaling, the important insight is that **"pay for what you use" is a metering problem, not an orchestration problem.** Vercel's own model moved to Fluid compute with Active CPU pricing — bill Active CPU (~$0.128/hr US), provisioned memory (~$0.0106/GB-hr), and invocations, pausing instances between requests. Notably this design *avoids* cold starts rather than embracing scale-to-zero. You can replicate that billing model by metering CPU-seconds and GB-seconds out of cAdvisor/Prometheus without adopting any serverless machinery. Scale-to-zero then becomes your own margin optimization, applied where cold starts are acceptable (preview and idle apps), not a product requirement.

That reframing is what lets a small team skip Knative. Knative is mature — CNCF graduated Sept 2025, v1.23.0 released 2026-07-29 — and its Revision model maps beautifully onto "every git push is an immutable deployment." But it brings a whole networking layer (Kourier/Istio/Gateway API) on top of the gateway you already need, an activator in the request path, and a queue-proxy sidecar on every pod. That last one directly costs tenant density on hardware you paid for, and density is the whole economics of self-hosting. Research shows cold starts pushing median latency from ~90ms to over 2s at 20% cold-start mix.

On progressive delivery, Argo Rollouts is clearly the healthier project. Flagger ships roughly twice a year (v1.40 Dec 2024, v1.41 Apr 2025, v1.42 Oct 2025, v1.43 Apr 2026, v1.44 Jul 2026); Argo Rollouts shipped v1.9.0 Mar 2026, v1.9.1 Jul 2026 and v1.10.0-rc1, with a Gateway API traffic-router plugin (v0.13, Jun 2026) that added header-based routing — precisely what preview URLs and canary-by-header need.

For isolation, gVisor and Kata are both healthy (gVisor releases weekly; Kata 4.1.0 Aug 2026, now Rust runtime-rs by default with the Go runtime deprecated). gVisor wins on density and startup; Kata wins on hard isolation. Northflank — the closest comparable, also serving untrusted code — runs both, defaulting to microVMs and falling back to gVisor where nested virtualization is unavailable.

**Recommendation:** **Build v2 on plain Deployments + KEDA + Argo Rollouts, with gVisor and user namespaces as the isolation boundary, on Cilium. Do not adopt Knative. Do not adopt vCluster.**

**Concrete topology — one kubeadm cluster, Kubernetes 1.36, four node pools:**

- `pool=system` (3 nodes, tainted `NoSchedule`): Cilium Gateway, cert-manager, Prometheus, KEDA, Argo Rollouts. Customer pods never land here.
- `pool=build` (2-4 nodes, tainted): rootless BuildKit pods under gVisor, egress-restricted, ephemeral, holding **zero cluster credentials**. This is the direct fix for the v1 RCE where the build container carried a kubeconfig plus Docker Hub push creds. Builds push to a registry with a short-lived scoped token; a separate in-cluster controller applies manifests. Builds are the most dangerous workload you run — arbitrary customer Dockerfiles and repo contents — so treat the build pool as hostile.
- `pool=runtime` (N nodes, tainted): customer apps. `runtimeClassName: gvisor` + `hostUsers: false` on every pod, no exceptions.
- `pool=isolated` (later): Kata + QEMU for a paid hard-isolation tier.

Taints give you scheduling separation and blast-radius control; they are explicitly **not** a security boundary. The boundary is gVisor plus user namespaces.

**Per tenant:** one namespace carrying default-deny ingress *and* egress NetworkPolicy (explicitly blackholing 169.254.169.254 — this also closes the v1 SSRF via `deployment_url`), a ResourceQuota, a LimitRange, PSA `restricted` enforced via namespace labels, and `automountServiceAccountToken: false`. Generate all of it from one templated function so a tenant cannot exist without its policies. Kyverno only if you need checks beyond PSA's three profiles.

**Choose 1.36 specifically**, not 1.34 (EOL 2026-10-27, two months away) — 1.36 is where user namespaces went GA and runs until 2027-06-28.

**Serving:** one Deployment per deployment-id, fronted by Gateway API HTTPRoutes. Preview URLs are a routing concern, not a serving concern — this is the insight that lets you skip Knative entirely. Use Argo Rollouts **blue-green** for customer deploys (build new, health-check, swap active service, keep the old ReplicaSet for instant rollback) because that *is* the Vercel model, and canary for your own platform components.

**Autoscaling:** HPA v2 on CPU/memory as the floor, KEDA as the single autoscaling brain for everything else. Run KEDA **or** prometheus-adapter, never both — they collide on the external metrics API. Add the KEDA HTTP add-on for scale-to-zero on preview/hobby apps only; it is still beta at v0.15.0 with API churn (HTTPScaledObject deprecated in v0.14.0), so keep it off the production request path until v1.0.

**Billing:** meter CPU-seconds and GB-seconds from cAdvisor via Prometheus and bill Vercel-style (active CPU + provisioned memory + invocations + egress). Run metering as a cluster-side controller on a fixed schedule — v1's fatal bug was bandwidth metering that only ran when the customer opened their own dashboard, making overage billing opt-in by the customer.

**Two changes to make immediately, before any v2 work:** replace ingress-nginx (retired, permanently unpatched, internet-facing) and upgrade off Kubernetes 1.31 (EOL since Nov 2025).

**Also replace, while you have zero migration burden:** Docker Hub `hav0ky` → self-hosted **Harbor** (per-tenant projects, robot accounts, retention policies that fix the unbounded-image-growth bug, Trivy scanning, and a data-residency story that matters for a sovereign-cloud pitch in India). Jenkins + ~10k lines of generated pipeline XML → **Cloud Native Buildpacks** (CNCF graduated 2026) driven by plain Kubernetes Jobs. Buildpacks auto-detect the framework, which eliminates both the 14 near-duplicate pipelines and the v1 flaw where framework was user-selected rather than server-detected. Use **DNS-01 wildcard certs** via Cloudflare for `*.apps.yourdomain` — per-app HTTP-01 will hit Let's Encrypt's 50-certs-per-registered-domain-per-week limit and take the platform down.

**Honest operational cost.** This is roughly 3-5 months of focused work for two or three engineers before first customer traffic, and it is not zero-maintenance afterwards. The recurring burden: a Kubernetes minor upgrade every ~6 months against a 14-month EOL clock (the treadmill that produced your current EOL 1.31); containerd runtime-handler configuration drift on every runtime node, which must be automated in the node image or it will rot; gVisor's weekly releases (you do not need to track every one, but you must not drift a year); and a real support cost from the minority of customer images that hit gVisor syscall gaps — you will need a documented escape hatch (the Kata tier) and a way to diagnose those. Budget roughly 0.5 FTE ongoing for cluster operations alone. That is the genuine floor for running untrusted multi-tenant workloads on your own hardware. Anything claiming less is not counting the upgrade treadmill.

**What NOT to do:** do not run untrusted customer code on stock runC — the Nov 2025 CVEs make that an accepted breach, not a risk. Do not add Knative and a service mesh; that is the architecture that needs the 30-person platform team. Do not do per-tenant clusters. And do not build scale-to-zero for production traffic in v1 — Vercel itself moved *away* from that toward keeping instances warm and billing active CPU.

### edge-network

The ground has shifted under v1's stack. ingress-nginx is dead: the Kubernetes Steering and Security Response Committees announced retirement effective March 2026, repos are archived read-only, and there will be no further releases, bug fixes, or security patches. The planned successor InGate never matured and was retired with it. The committees' words are blunt: remaining on it "leaves you and your users vulnerable to attack." v1's ingress layer is therefore not a thing to improve — it is an unpatched dependency that must be replaced.

The replacement is the Gateway API, now genuinely mature. v1.4 GA'd Nov 2025; v1.5 (2026) promoted ListenerSet, TLSRoute, HTTPRoute CORS, and client-cert validation to Standard; v1.6 (June 2026) graduated TCPRoute/UDPRoute and moved experimental resources to a separate `gateway.networking.x-k8s.io` group. ingress2gateway hit 1.0 in March 2026 and translates 30+ ingress-nginx annotations. Envoy Gateway is at v1.8.0 (May 2026), bundling Gateway API v1.5.1, with deferred stat creation, bandwidth limiting, and GeoIP authz.

Two constraints dominate a many-domain PaaS. First, a Gateway is capped at **64 listeners**. Per-customer-domain TLS means one listener per domain, so you hit the ceiling at 64 customers. ListenerSet (GEP-1713) lifts this, but cert-manager's support landed only in 1.20 (March 2026) as an alpha feature behind a feature gate, with stable support deferred to 1.21/1.22. Building a commercial product on that today is building on alpha.

Second — and this is the trap v1 is sitting on — Let's Encrypt allows **50 certificates per registered domain per week**. v1's `dns.ts` creates a per-app unproxied A record at `<app>.galaxyhvh.com` and cert-manager issues a per-app HTTP-01 certificate. Every app shares one registered domain, so the platform bricks its own TLS at ~50 new apps per week. Because platform_apps is empty, this has never fired — it would fire in week one of launch. Other live limits: 300 new orders/account/3h, 5 duplicate certs/week, 5 failed validations/hostname/hour (a customer with wrong DNS burns this). Vercel solves it exactly one way: a single **wildcard cert via DNS-01** for `*.vercel.app`, plus per-customer-domain HTTP-01 certs. Also note Let's Encrypt is moving to 45-day certs (opt-in `tlsserver` profile from 13 May 2026, default in Feb 2028) and cutting authorization reuse from 30 days to 7 hours — any hardcoded 60-day renewal breaks; ARI support is now mandatory in practice.

The decisive insight: if a SaaS edge terminates public TLS, the origin needs **no per-customer certs and no per-customer listeners at all**. The 64-listener problem, the ListenerSet alpha dependency, and most Let's Encrypt exposure all evaporate. Cloudflare for SaaS does this for $0.10/hostname/month beyond 100 free, up to 50,000, and Regional Services can pin TLS termination and WAF processing to India — which is what makes it survivable for sovereign positioning. The honest catch is that Data Localization Suite requires account-team approval and is effectively Enterprise-gated, so India-pinning is a sales conversation with real money attached, not a checkbox.

v1's single-node host-network DaemonSet on a hardcoded KUBE_IP is simultaneously a single point of failure, a scaling ceiling, and an IP you can never change. Fixing that is less about a load balancer than about deleting every literal IP from DNS.

**Recommendation:** **Pick this: Cloudflare for SaaS at the public edge + Envoy Gateway inside the cluster + a shrunken cert-manager. Then build a second, fully-in-country path as a premium "sovereign tier" rather than as the default.**

Concretely, what the single-node host-network ingress must become:

1. **Delete every literal IP from DNS — this is the highest-priority change.** `lib/services/dns.ts` currently creates a per-app `type: "A"`, `proxied: false` record at `<app>.galaxyhvh.com` pointing at a hardcoded KUBE_IP. Replace with a single proxied wildcard for platform subdomains, and for customer domains issue a CNAME target (`cname.<platform>.in`) plus a Cloudflare Custom Hostname API call. As long as customer DNS contains your IP, you can never move, scale, or fail over. Nothing else on this list is possible until this is fixed.

2. **Fix the Let's Encrypt trap before launch, not after.** Stop issuing a certificate per app on the shared apex. Issue **one DNS-01 wildcard** for `*.<platform domain>` — the Vercel pattern. Constrain preview/deployment URLs to a **single DNS label** (`myapp-a1b2c3.ahuraapps.in`, never `branch.myapp.ahuraapps.in`), because a wildcard covers one level only. Without this you brick your own TLS at roughly the 50th app.

3. **Replace ingress-nginx with Envoy Gateway**, Deployment (not DaemonSet), 2+ replicas across a small dedicated edge node pool, fronted by a **MetalLB L2** VIP. Use ingress2gateway 1.0 to convert existing manifests. Because Cloudflare terminates public TLS, the origin serves **one** origin certificate and matches tenants by Host header on HTTPRoutes — so you never touch the 64-listener cap and never depend on cert-manager's alpha ListenerSet gate. That simplification is the main reason this combination wins.

4. **Lock the origin.** Cloudflare Authenticated Origin Pull (mTLS) plus a firewall accepting only Cloudflare ranges. Otherwise the origin IP leaks and every DDoS/WAF control is bypassable.

5. **Enable ARI in cert-manager now.** With 45-day certificates arriving (opt-in 13 May 2026, default Feb 2028) and authorization reuse dropping to 7 hours, any hardcoded 60-day renewal assumption breaks.

**Honest operational cost.** Envoy is the real learning investment — budget two to three weeks to get fluent with config dumps and xDS, and expect Envoy to be the thing you page on. Cloudflare for SaaS at $0.10/hostname/month is negligible, but **Regional Services/DLS is account-team-gated and effectively Enterprise**, so India-pinned TLS termination is a contract negotiation with real annual cost — get that quote before you build the sovereignty marketing around it. MetalLB L2 gives you seconds-not-milliseconds failover and one node's NIC of origin bandwidth; both are acceptable behind a CDN and neither is acceptable without one.

**The sovereignty caveat, stated plainly.** Routing through Cloudflare means a US company terminates TLS for Indian customers. Under DPDP as of 2026 this is legal — no countries are currently notified as restricted, and RBI localization bites only payment data. But it will fail MeitY-empanelment-style government tenders and it weakens the "sovereign cloud" claim. So do not pretend otherwise: sell the Cloudflare-fronted tier as the default commercial product, and offer a genuinely in-country tier — **Caddy fleet with On-Demand TLS** in front of the same Envoy Gateway, shared CertMagic storage, Coraza/OWASP CRS for WAF — for regulated buyers, priced to cover the extra operational load. Caddy, not cert-manager-per-domain, is the right engine for that path: it was built for exactly this problem and a small team can actually run it.

**What to reuse from v1:** cert-manager (scoped down), Cloudflare DNS (now as CNAME targets and Custom Hostnames rather than A records), and the domain-verification TXT flow in `config/domain.ts`. **What to discard:** ingress-nginx, the hardcoded KUBE_IP, per-app A records, and per-app HTTP-01 certificates on the shared apex.

**Verifier verdict:** The recommendation survives scrutiny on its core direction, but not on several of its stated justifications, and one pillar of the sovereign tier may not exist.

What does not hold up: the urgency framing for the wildcard is simply wrong — renewals are exempt from Let's Encrypt rate limits, so there is no wall at 50 apps, only a 50-new-hostnames-per-week throughput ceiling. The right conclusion for a different reason (preview deployments burn that budget fast), and the Public Suffix List option that would remove the limit entirely is not mentioned at all. Envoy Gateway's claimed uniqueness on declarative HTTP rate limiting is refuted by Traefik OSS. The cert-manager section is written against 1.20 when 1.21 has shipped, and 'enable ARI now' is not a toggle on the version cited. Caddy's scale evidence is a misreading of dollars as sites.

The one finding that should change the plan rather than just correct it: Regional Hostnames — the only Regional Services path that works with Cloudflare for SaaS custom hostnames — supports managed regions only, and I could not confirm India is among them; the reachable Cloudflare docs list only US, EU and Canada. So 'Enable ARI in cert-manager now' requires an upgrade to 1.21 plus a feature-gate flag. ListenerSet remains EXPERIMENTAL in 1.21, so that risk assessment is unchanged (v1.22 is planned ~Nov 2026).
- The sovereign tier's Cloudflare leg may not exist, and this is the biggest hole. Regional Hostnames is the only Regional Services option that works with Cloudflare for SaaS custom hostnames, and it supports MANAGED REGIONS ONLY — the docs explicitly redirect custom-region needs to Spectrum or IP Bindings, neither of which applies to custom hostnames. I could not confirm India is an available Regional Hostname region; the reachable pages list only US, EU, and 'ca'. Upgrade the recommendation's 'get a quote first' to a hard gate: CONFIRM INDIA IS AN AVAILABLE REGIONAL HOSTNAME REGION before any sovereignty positioning is written. If it is not, the Caddy path is not a premium upsell, it is the only in-country option, and the Cloudflare tier cannot be sold as India-pinned at all.
- The document is internally incoherent about which tier owns certificate strategy. Point 3 says Cloudflare terminates public TLS and the origin serves ONE origin certificate matched by Host header — in that architecture the origin has almost no Let's Encrypt surface at all. But points 2 (DNS-01 wildcard) and 5 (ARI in cert-manager) only matter for the in-country Caddy tier, and Caddy/CertMagic runs its own ACME without cert-manager anyway. Split the cert plan explicitly by tier; as written it reads as one shared strategy and it is not.
- Envoy Gateway should not be selected on the stated rate-limiting differentiator, because that differentiator is false. Traefik OSS ships declarative HTTP rate limiting (token bucket, Kubernetes CRDs, Redis-backed distributed mode) in the open-source build. 'Only major Gateway API implementation with native declarative HTTP rate limiting' is refuted; 'only one with BackendTrafficPolicy' is a tautology since that is an Envoy-Gateway-specific CRD. Envoy Gateway may still be the right pick — but justify it on conformance, CRD freshness (v1.5.1 bundled), and ListenerSet handling, not on a uniqueness claim that does not hold.
- The MetalLB analysis omits the cost that matters most for the BGP escape hatch. The recommendation accepts L2's one-NIC ceiling as 'acceptable behind a CDN' and implies BGP as the growth path. But MetalLB's own BGP docs warn that on any node or backend change, 'the majority of existing connections will end up suddenly being forwarded to a different backend' — BGP mode breaks live connections on every rebalance. Budget for that, or plan to keep an ingress controller as the stateful intermediary the docs recommend as mitigation.
- Two Enterprise gates are unstated and both affect pricing. Cloudflare wildcard custom hostnames, custom certificates, CSR support, selectable CA, and mTLS are ALL Enterprise-only on Cloudflare for SaaS — so the $0.10/hostname figure buys a materially less capable product than the note implies. Note that Cloudflare Authenticated Origin Pull (recommended in point 4) should be confirmed against your actual plan tier before it is treated as available.
- Traefik's exclusion is correct but the stated reason is not. The KV store was REMOVED in Traefik 2.0 for poor performance — it is not an HA requirement, it is an unavailable path. The '~100 ACME certificates via Consul' figure appears in no Traefik documentation. Keep the conclusion, drop the reasoning.
- Two smaller sourcing errors to strike before this circulates: Caddy's 'tens of thousands' refers to DOLLARS saved, not sites served — no site count or named production user appears on the cited page. And Vercel's docs confirm the HTTP-01/DNS-01 split but never state that *.vercel.app runs on a single wildcard certificate; that specific detail is inference presented as sourced fact.
- Three claims could not be checked at all and should carry that label: Cloudflare's Indian edge footprint and sub-50ms latency (site returned 403); the IRINN/APNIC ASN and delegation pricing (site returned 503, and quoting IRINN fees in AUD conflates the Indian NIR with APNIC, which bills in AUD while IRINN bills in INR); and the DPDP 'no countries currently restricted' plus RBI-payment-data-only assertions (MeitY source returned 403). The DPDP one is not a research question — the DPDP Rules and Significant Data Fiduciary obligations can impose localization duties beyond Section 16. ### oss-paas-prior-art

The 2026 landscape splits into four tiers, and only one of them is actually adoptable.

**Tier 1 — single-host Docker PaaS (Coolify, Dokploy, CapRover, Dokku).** These are the popular ones, and they are all architecturally disqualified for you. Coolify (Apache-2.0, 61k stars, extremely active) is explicitly a Docker-per-host product: its own multi-server docs call the feature "experimental," the load balancer is manual, and Kubernetes is "planned, not on the roadmap." The v5 rewrite that fixes multi-server has no public date. Dokploy (36.9k stars) is Docker Swarm. CapRover and Dokku are Swarm and single-host respectively. Adopting any of these means throwing away your Kubernetes cluster and inheriting someone else's single-box ceiling.

**Tier 2 — Kubernetes-native OSS PaaS (Kubero, Qovery Engine, Porter).** Thinner than they look. Kubero is a GPL-3.0 operator + UI with real review-app pipelines but only 4.4k stars and a small maintainer base. Qovery Engine is a genuinely good Rust orchestration library (Terraform + Helm + kubectl) but is GPL-3.0 and is designed around Qovery's cloud-provider provisioning, not your bare-metal cluster. **Porter is gone as an option: `porter-dev/porter` now 404s — the OSS core has been taken private and Porter is a closed commercial BYOC product.**

**Tier 3 — runtime cores (Knative, Korifi).** Knative graduated CNCF in Sept 2025, is very actively developed, and its Service/Revision/Route model maps almost 1:1 onto Vercel's immutable-deployment + traffic-split + instant-rollback semantics. It is the strongest technical candidate — with one damning data point: Render, a real Vercel competitor, *did* run Knative at 100k+ apps, had to fork it to delete the 3 Kubernetes Services that Knative creates per app (which was melting Calico and kube-proxy — the exact CNI you run), and said the time was "quickly approaching" to replace Knative entirely. Red Hat documents a practical ceiling around 3,000 Knative Services for the same reason. Korifi is worse: Apache-2.0 and nominally alive, but still pre-1.0 after five years (v0.18.0, March 2026), only 408 stars, and **no commits on `main` since late May 2026**. It is a CF-API-compatibility project, not a product foundation.

**Tier 4 — commercial reference architectures (Railway, Render, Fly.io, Northflank).** Not adoptable, but the best design source. Railway runs BuildKit inside microVMs on 256-vCPU bare metal with a consistent-hash scheduler to keep build caches warm — 66k builds/hour. Fly.io wrote `flyd` because Nomad bin-packed wrong and couldn't do synchronous scale-from-zero. Northflank does exactly your shape: namespace isolation + NetworkPolicy + gVisor/Kata on Kubernetes.

**Two facts that override the whole decision.** `kubernetes/ingress-nginx` **is archived as of March 2026** — last commit 2026-03-19, no further releases, no CVE fixes ever. Your v1 depends on it as a host-network DaemonSet with a hardcoded `KUBE_IP`. And Kubernetes v1.31 is past upstream EOL; supported lines are 1.34/1.35/1.36. You have to rebuild the edge and upgrade the cluster no matter which option you pick, so the migration cost is sunk — it should not bias you toward adopting a PaaS engine to "avoid work."

Also retired: Kaniko (archived June 2025) and Nixpacks (maintenance mode, superseded by Railway's Railpack, MIT, BuildKit-based).

**Recommendation:** **Build it in-house — option (a) — but build it thin, on vanilla Kubernetes primitives, with named off-the-shelf components for every hard sub-problem. Do not adopt an OSS PaaS engine, and do not put Knative or Korifi underneath the product.**

The reasoning, in order of weight:

1. **The migration cost you were trying to avoid is already sunk.** `kubernetes/ingress-nginx` is archived (last commit 2026-03-19, no more CVE fixes ever) and your Kubernetes v1.31 is past upstream EOL. You are rebuilding the edge and upgrading the cluster regardless. So "adopting an engine saves work" is false — every option costs you the same edge rebuild, and the engine options cost you that *plus* a new control plane to learn.

2. **Every adoptable engine fails on a hard constraint, not a soft preference.** Coolify/Dokploy/CapRover/Dokku are not Kubernetes. CapRover's license appendix explicitly forbids what you want to do. Dokploy's DSAL forbids production use of /proprietary without their commercial agreement. Kubero and Qovery are GPL-3.0, which is fine for pure SaaS but forecloses the on-prem/air-gapped deals a sovereign-cloud vendor in India will eventually be asked for. Porter's OSS core is gone. Korifi has been silent on main since May 2026.

3. **Knative is the only serious (c) candidate, and the best evidence available says no.** Render ran it at your target quality bar and had to fork it to delete the three Kubernetes Services per app that were saturating Calico and kube-proxy — you run Calico. Red Hat documents a ~3,000-Service ceiling for the same reason. Render said they were approaching the point of replacing it. A handful of engineers should not adopt a runtime whose most credible operator was planning an exit.

4. **The product model you want is trivially expressible in raw Kubernetes.** A Vercel deployment is: immutable build artifact, immutable Deployment, and a routing weight. That is `Deployment` + `Service` + `HTTPRoute`. Instant rollback is a weight change. Preview environments are just more Deployments behind a wildcard host. You do not need a framework for this — v1's problem was never that Kubernetes lacked primitives, it was 6,000 lines of fire-and-forget glue in `jenkins.ts`, `kubernetes-custom-domain.ts` and `build-polling.ts` with no reconciliation loop.

**The named v2 stack:**

- **Cluster:** Talos Linux (MPL-2.0, v1.13.x/1.14-rc, very active) on your own hardware, Kubernetes 1.34+. API-driven, immutable, no SSH — this deletes the entire `vm_kubernetes` SSH-provisioning repo and is a genuine sovereignty win (no cloud vendor in the control path).
- **Edge:** Gateway API with **Envoy Gateway** (Apache-2.0, v1.9.0 shipped 2026-08-15). Migrate off ingress-nginx now; use `ingress2gateway` (1.0, March 2026) to translate. Drop the hardcoded single `KUBE_IP` for multiple Gateway addresses.
- **TLS:** cert-manager for the platform wildcards (`*.ahuracloud.app`, `*.preview.…`) via DNS-01. For **customer custom domains, use Caddy on-demand TLS at the edge with an ask-endpoint hitting your Supabase-backed API** rather than thousands of cert-manager Certificate CRs — Let's Encrypt is moving to 64-day then 45-day certs, which roughly doubles renewal volume, and on-demand issuance keeps that off your control plane.
- **Builds:** kill Jenkins entirely. Run a **BuildKit** pool (Apache-2.0) and drive it over gRPC from your reconciler. Use **Railpack** (MIT, Railway's BuildKit-native successor to Nixpacks) for zero-config framework detection, with Dockerfile passthrough. Copy Railway's consistent-hash "route this app to the node holding its cache" scheduler — it is the single highest-leverage build optimization. Do **not** use Kaniko (archived June 2025).
- **Registry:** self-host **Harbor** (or zot if you want minimal). The shared Docker Hub `hav0ky` namespace is both a tenant-isolation hole and a foreign dependency that undercuts the sovereign-cloud pitch.
- **Isolation:** namespace per project, default-deny NetworkPolicy, ResourceQuota + LimitRange, and **gVisor via RuntimeClass** for customer code (Northflank's model). User namespaces went GA in Kubernetes 1.36 — turn them on once you're there.
- **Scale-to-zero:** KEDA HTTP add-on if you want it, or skip it in v2.0 and run a low replica floor. Do not adopt Knative just for this.
- **Control plane:** Supabase stays the system of record. Add **one Go or TypeScript reconciler service** that reads desired state and continuously reconciles observed state, with exponential backoff and a real state machine. Next.js route handlers must never call the Kubernetes API directly — that pattern is exactly what produced v1's stuck-deployment bugs.

**Honest operational cost.** Roughly two engineers for four to six months to a credible v2 GA, then about one FTE-equivalent of ongoing platform work forever. The genuinely hard parts nobody warns you about: build-cache placement (Railway rebuilt this three times), log ingestion and retention at per-tenant granularity, registry garbage collection, node pressure and eviction behaviour when a tenant's build OOMs a node, and certificate renewal reliability once you have a few thousand custom domains. Budget an on-call rotation. But note this is *less* operational cost than the alternatives, not more — adopting Knative or Korifi adds a second control plane to that same on-call scope without removing any of the five hard parts, because all five live in the product layer you'd still be writing yourself.

**The one thing to reuse from v1:** the Supabase-as-system-of-record decision, and the domain-verification/DNS-checking logic in `lib/domain-service/` — that is real product knowledge. Discard `jenkins.ts` entirely.

**Verifier verdict:** Yes, the recommendation survives scrutiny — the conclusion is sound and the evidence base is unusually well-sourced for this kind of write-up. 19 of 21 claims verified clean against primary sources; the two problems (Korifi's release date being a year off, and the Render post being four years old and presented as current) are real errors but neither reverses the argument. Every licence claim — the ones researchers most often botch — checked out verbatim: CapRover's appendix, Dokploy's DSAL, Coolify's unmodified Apache-2.0, Kubero and Qovery at GPL-3.0. The repo-side claims are exact: the 6,069 lines across the seven orchestration files are correct file-for-file, and the KUBE_IP/ingress-nginx coupling is in fact WIDER than stated (it also reaches all 11 Jenkins pipeline templates, lib/services/prometheus.ts, and the bandwidth ingress annotations).

The load-bearing logic holds where it matters most. Argument 1 — that the migration cost is already sunk — is the strongest part and is fully verified: ingress-nginx is archived and will never receive another CVE fix, and Kubernetes 1.31 went EOL in November 2025, so the edge rebuild and cluster upgrade are unavoidable regardless of which path is chosen. That genuinely does neutralise 'adopting an engine saves work.' Argument 2 is airtight: every adoptable engine fails on a verified hard constraint, not a preference. Argument 4 is a design judgement rather than a factual claim, but it is a defensible one, and the repo evidence supports the underlying diagnosis — the existence of a /recover-build endpoint is a fossil of exactly the fire-and-forget, no-reconciler problem being described.

Argument 3 is where I would push back hardest. The case against Knative rests on a 2023 blog post describing 2022 work, cited without its date, while the write-up's own claim 12 concedes Knative has since graduated in CNCF and is migrating to Gateway API — the very layer Render was fighting. That is not disqualifying, because the Service-multiplication architecture is independently confirmed still-open in knative/serving#13201 and nobody has published evidence it was fixed. But 'the best evidence available says no' overstates it. The honest version is 'a credible operator hit this hard in 2022, the underlying issue is still open upstream, and nobody has shown it resolved' — which still supports not adopting Knative, just less theatrically.

Pick one, or name the concrete integration. Second, the cost section omits gVisor's syscall-performance penalty, which is material for a Node/Next.js PaaS and belongs alongside the five hard parts already listed. ### platform-ops

Five things forced this analysis to a firm answer rather than a survey.

**1. Your v1 gateway is dead, and it takes your metering with it.** kubernetes/ingress-nginx retired 31 March 2026 — no security patches, ever again. This is not a "plan a migration someday" item: `lib/services/platform-app-bandwidth/constants.ts` enforces bandwidth quotas via `nginx.ingress.kubernetes.io/server-snippet`, the exact annotation class behind IngressNightmare (CVE-2025-1974, CVSS 9.8, unauth RCE). Your bandwidth accounting AND custom-domain handling are both built on an unmaintained, RCE-prone controller. v2 must be Gateway API. Fortunately Envoy Gateway gives you per-HTTPRoute byte counters and declarative rate limiting — which is precisely what honest bandwidth metering needs. The forced migration and the metering fix are the same piece of work.

**2. One database can serve logs, traces, per-app metrics, AND the billing meter.** The classic answer is the Grafana LGTM stack, but Loki holds 6–7 GB RSS where VictoriaLogs holds 1.3 GB for the same load, ships as a fleet of microservices, and — decisively — cannot aggregate your usage events. ClickHouse can. Customer-facing build/runtime logs, per-app metric rollups, and the CPU-second/byte/build-minute ledger are all the same shape: high-volume append-only events aggregated by tenant over time. OpenMeter itself is Kafka + ClickHouse. Running one ClickHouse instead of Loki + Mimir + a separate meter store collapses three systems into one for a team that cannot staff three.

**3. Customer env vars are not a secrets-manager problem.** ESO, Vault, Infisical, SOPS, and sealed-secrets all solve "get platform secrets from an external store into a cluster." Customer env vars are different: tens of thousands of rows, customer-editable through your UI, and your control plane must read them anyway. Routing them through a second system of record creates drift for zero benefit. Today `platform_app_env_vars.value` is plaintext `TEXT`. The fix is envelope encryption in Postgres with per-tenant KEKs held *outside* Postgres — which also means **not** Supabase Vault/pgsodium, since pgsodium is pending deprecation and, more importantly, keeps the key in the same database as the ciphertext, so one dump is game over.

**4. Never imperatively kubectl-apply — but "GitOps" is also the wrong shape.** Your v1 already has `k8s-discovery.ts` (scan the cluster, cross-reference the DB) and `infrastructure-cleanup.ts` (find orphans). Those files are drift detection and partial-failure cleanup bolted onto an imperative design; they are the symptom, not the cure. But Argo CD/Flux assume Git is truth and a human is the actor. In a PaaS, the customer's dashboard click is the actor and Postgres is truth. Git in the hot path of an env-var edit is latency, a secret-bearing artifact, and a scale ceiling (Argo's 2026 user survey names scaling as the top complaint past ~2,000 Applications).

**5. DPDP does not mandate localisation — which makes it a sales asset, not a constraint.** Rule 15 permits transfer abroad by default, subject to restrictions the Central Government "may, by general or special order, specify." The government holds a standing power it has not yet used. Being already immune to a restriction that could land any Tuesday is the product you are selling. Full substantive compliance is due 13 May 2027.

**Recommendation:** Build the v2 platform-ops layer on **ClickHouse + OpenTelemetry Collector + Envoy Gateway + a custom Go reconciler + OpenBao Transit + Ory Polis**, with **Argo CD strictly for platform infrastructure and never for customer apps**.

**Observability — ClickHouse, one cluster, three jobs.** Run the OpenTelemetry Collector (not Grafana Alloy — Alloy is fine but ties you to Grafana's ecosystem, and OTel Collector is the vendor-neutral reference implementation; note Promtail hit EOL 2 March 2026 so it is not an option either) as a DaemonSet shipping container logs, and as a deployment receiving OTLP from build pods. Everything lands in ClickHouse. Use ClickStack for the engineer-facing UI immediately; build the customer-facing log viewer in Next.js with direct SQL against a restricted, per-tenant-filtered role. Keep Prometheus 3.x + Alertmanager for infrastructure alerting only, ~15-day retention, no remote-write to anything. Ship **log drains** early — Vercel Drains covers runtime, build, static asset, firewall, and function logs plus OTLP traces, in JSON/NDJSON/Protobuf. Copy that surface; it is table stakes for enterprise buyers and it is also your DPDP escape hatch, since a customer who wants their logs in their own SIEM should be able to have them.

**Secrets — envelope encryption in Postgres, KEKs in OpenBao.** Replace `platform_app_env_vars.value TEXT` with `ciphertext BYTEA, nonce BYTEA, dek_id UUID, key_version INT`, AES-256-GCM, AAD bound to `(app_id, key_name)` so a ciphertext cannot be replayed into another app or renamed. Per-app DEK, wrapped by per-tenant KEK, KEK living only in OpenBao's Transit engine. **OpenBao, not Vault**: Vault has been BUSL 1.1 since August 2023 and IBM-owned since early 2025, and BUSL's competing-hosted-service restriction is aimed at businesses that look exactly like yours. Run Transit only — that is a fraction of full Vault's operational weight. Enable Kubernetes `EncryptionConfiguration` so etcd is not storing your customers' secrets in plaintext. Use ESO for your ~20 platform secrets and nothing else. Do not use Supabase Vault/pgsodium: pgsodium is pending deprecation, and it stores the key beside the ciphertext.

**Desired state — your own CRD, no Git in the hot path.** One `App` CRD per app revision. The control plane's only cluster write is a single idempotent CR upsert; a Kubebuilder controller fans out to Deployment, Service, HTTPRoute, Certificate, NetworkPolicy, ResourceQuota, and the env Secret, and mirrors `.status` back into Postgres. This deletes the reason `k8s-discovery.ts` and `infrastructure-cleanup.ts` exist. Argo CD gets the platform repo — ClickHouse, OpenBao, cert-manager, Envoy Gateway, the operators, monitoring — roughly 50 Applications, well inside its comfort zone, and it buys you rebuild-the-cluster-from-scratch. Two problems, two tools. If nobody can write Go, prototype **kro** first, but treat that as a bet.

**Metering — events, not queries.** A one-minute aggregator reads `container_cpu_usage_seconds_total` and `container_memory_working_set_bytes` from Prometheus and writes usage *events* (`app_id, resource, quantity, window_start, window_end, idempotency_key`) into ClickHouse on a ReplacingMergeTree keyed by idempotency_key, so replays are safe. Never invoice off a live Prometheus query — Prometheus is lossy, has short retention, and its counters reset on pod restart. Build minutes come from the controller recording build-pod start/finish, with a hard timeout and a per-team concurrency cap. Bandwidth comes from Envoy per-HTTPRoute byte counters, replacing the ingress-nginx annotation scheme entirely. Decide now whether you count TLS overhead and response-only or both directions, and publish it — customers will diff your number against theirs. Keep invoicing in your existing Postgres tables for now; adopt Lago only when you need proration and credits.

**Compliance — hash-chain the audit log, buy the SSO.** Your `inference.audit_log` is already monthly-partitioned; reuse that shape for a platform-wide audit log and add `seq`, `prev_hash`, and `hash = sha256(prev_hash || seq || canonical_json(row))`, with the app role granted INSERT and SELECT only — no UPDATE, no DELETE. That makes tampering mathematically detectable and gives you an artifact an auditor will accept. Supabase Auth covers SAML 2.0 SSO; add Ory Polis for the SCIM 2.0 directory sync it does not. RBAC: Organization → Team → Project → Environment in Postgres with RLS, and a policy test suite in CI — non-negotiable, given the live RLS gap already in your production database.

**On DPDP, be precise in your marketing.** Rule 15 permits cross-border transfer by default, subject to restrictions the Central Government may impose by general or special order; there is no blanket localisation mandate today, but the power is standing and unexercised, and for Significant Data Fiduciaries the government may bar offshore transfer of specified data categories outright. Full compliance lands 13 May 2027; penalties reach ₹250 crore per violation. So do not claim the law forces localisation — claim that you are already immune to a restriction that could arrive with no notice. That argument is stronger, it is true, and it independently justifies self-hosting the whole observability stack rather than piping customer logs to a US SaaS. **One thing to verify immediately: if your Supabase project is not in ap-south-1 (Mumbai), your control plane already violates the sovereignty claim you are selling.**

**Honest operational cost.** This is roughly one engineer-quarter to first production traffic, then about 0.5 FTE ongoing. The three genuinely hard, non-delegable pieces are: operating replicated ClickHouse (schema and ORDER BY key decisions you cannot cheaply undo), writing and testing the Go reconciler, and OpenBao unseal-key custody as a rehearsed procedure rather than a wiki page. Everything else is assembly. What makes this tractable for a handful of engineers is the deliberate collapsing: one datastore serving logs, metrics, and billing; one reconciler owning all convergence; one gateway providing both routing and metering. The failure mode to avoid is adopting the "correct" tool for each of the five concerns independently and ending up with eleven stateful services and nobody on call who understands four of them.

**Sequence it: (1) Gateway API migration — you are running an EOL, RCE-prone controller right now; (2) encrypt the env vars — they are plaintext today; (3) the CRD and reconciler; (4) ClickHouse and log drains; (5) metering; (6) SSO, SCIM, and the audit chain when the first enterprise deal demands them.** Items 1 and 2 are live security exposure and should not wait for the v2 design to be finished.
