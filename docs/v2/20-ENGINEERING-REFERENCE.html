Deploy v2

A Vercel-class application platform rebuilt from zero on Linode, Cloudflare and Kubernetes — after an audit found fourteen critical defects in the version it replaces, including remote command execution from a normal user account. This is the complete technical record: what was built, why each decision went the way it did, and what has been proven by running it rather than by reading the code.

01

Why there is a v2

v1 — the platform_apps service — was audited against real code by a 32-agent process: six subsystem audits, six research tracks each fact-checked by an independent skeptic, two substrate capability studies, and three competing architectures each scored by three adversarial judges. The audit returned 14 CRITICAL and 30+ HIGH findings.

The decisive fact for planning: platform_apps was empty in production. Zero apps had ever shipped. There was no migration burden, and therefore no reason to carry any of it forward.

The sharpest findings

#FindingWhy it was critical
1 RCE via the app's git branch name The branch was z.string().min(1) — no charset, no length — and was interpolated unquoted into git clone --branch ${branch} inside a Jenkins sh block. That agent held KUBECONFIG and the platform-wide webhook secret. Full cluster compromise from a normal user account.
2 The hardening pass silently did nothing hardenPipelineXml's regex required a whitespace-free branch. A branch containing a space skipped hardening entirely — no error, no log line, no test — leaving the original injectable line verbatim.
4 No tenant isolation of any kind Every customer app ran in the shared default namespace. No NetworkPolicy, no ResourceQuota, no PodSecurity, no securityContext, no sandbox. A grep for all eleven isolation primitives returned zero hits across the repository.
6, 10 Rename-to-take-over name was the K8s Deployment, Service and Ingress name, the Jenkins job name, the TLS secret name and the public hostname — with no UNIQUE constraint and no validation on the update path (create validated; update did not). Rename onto a victim's app, press Redeploy, and their live workload and hostname are yours.
3 Deleted apps leaked plaintext secrets The delete pipeline targeted {name}-app-env-secret; the Secret that existed was {name}-env-secret. Every deleted app left its DB URLs and API keys in the shared namespace forever — and the verification stage then printed [PASS].
7 Billing outlived the app it billed No FK, no cascade, and the delete endpoint passed the caller's user id where the owner's was required. This had already happened five times in production and the meters were still running.
8 Apps ran forever, unbilled A rate lookup failure returned hourlyRate 0, which violates the meter's CHECK constraint, so activation hard-failed — and the failure was downgraded to a warning string while the deploy reported success.
5 Hostname takeover with DNS verification skipped The registrar ownership probe queried one shared Name.com account with no user scoping and only tested that the response was truthy. Any domain in the platform's account auto-verified for any authenticated user.
14 A false claim that changed user behaviour The wizard said "the platform probes this endpoint before routing traffic." Probes were tcpSocket-only and the configured path was explicitly discarded.

The four root causes

Most of the 14 collapse into four decisions, and v2 is largely the inversion of them:

  • A mutable name as the primary key of all infrastructure addressing. One decision, three separate critical findings.
  • Shell and XML built by string interpolation — ~10k lines of near-duplicate Jenkins pipeline XML generated by template literals, with user input flowing straight in.
  • One shared everything — one namespace, one Docker Hub credential, one webhook secret, one registrar account.
  • Billing decoupled from lifecycle, with failures downgraded to warnings.

What v1 got right, and v2 kept

The audit was not a demolition. Carried forward: the Linode client's retry/backoff and capacity detection; bill_service_cycle_atomic's FOR UPDATE + CAS metering primitive; digest-pinned image refs; timing-safe per-app webhook HMAC; the section-allowlist build-log sanitiser; and the UNIQUE (domain) WHERE status <> 'removed' partial index, which is exactly the right shape for domain claims.

02

What the substrate forced

Three capability studies removed options rather than expressing preferences. These are constraints, not choices.

Linode has no hardware virtualization, anywhere

Nested virtualization is disabled platform-wide — it conflicts with Live Migration, and that has been a consistent staff position for eight years. Akamai also sells no bare metal: there is no metal class in the API type enum.

Therefore Kata Containers, Firecracker, Cloud Hypervisor and every in-cluster microVM design are impossible here. The sandbox must be gVisor (runsc), a userspace kernel that needs no /dev/kvm.

LKE's pod ceiling makes a fleet mandatory

Standard LKELKE Enterprise
Max nodes250500
Max pods per cluster1,0005,000
Control planeFree (HA +$60/mo)$300/mo per cluster
Version lifecycleForce-upgraded at EOLNot force-upgraded
AvailabilitySelf-serveRequires Akamai approval

At one pod per app, 10,000 apps fit in neither tier. A cluster-placement and sharding layer is required in the control plane from day one — it cannot be retrofitted. Two further traps: the HA control plane is irreversible and destroys all nodes when enabled, so every cluster must be created with it on; and LKE-E is gated on a sales conversation.

Cloudflare removes the TLS ceiling

v1's model — one Let's Encrypt certificate per app on a shared apex — caps growth at roughly 50 new apps per week. Cloudflare for SaaS removes it: platform subdomains cost zero custom hostnames, covered by one proxied wildcard record. Customer BYO domains are custom hostnames — 100 included, then $0.10/hostname/month, with a 50,000 self-serve ceiling. DCV Delegation makes renewals fully automatic.

Gates worth knowing now

Per-tenant WAF, wildcard custom hostnames and more than one rate-limit rule are Enterprise-only. At 10k untrusted tenants, per-tenant WAF is a requirement rather than a nicety — and this is still an open commercial decision.

Postgres holds every app; Kubernetes holds only the warm ones. Cloudflare terminates all public TLS; builds run one-per-throwaway-VM and hold no cluster credentials.

Where the built system diverged from the plan

The proposal named Harbor, Envoy Gateway and OpenBao. What shipped is Docker Distribution, Traefik v3 and AES-GCM-in-Postgres. Each swap traded a service to operate for one less thing that can break at 3am — the plan's own stated constraint was that operability is a first-class constraint for a small team, and three fewer standing services is that constraint applied.

04

The deploy pipeline

deployFromRepo in lib/paas/deploy.ts is the spine. It reports nine stages, and they are genuinely sequential — each depends on the last, which is why they are numbered here.

  1. 01
    detect

    Ask the provider for the default branch — never guess it. List the root directory in one call where the provider supports it, then read only the marker files that exist. Detection yields a framework, a runtime, a build command, an output directory and a port.

  2. 02
    project

    Resolve or create the project row, scoped to the caller's team. Records the provider, the repository, the production branch and the root directory.

  3. 03
    deployment

    An immutable row, keyed (environment, sha). A database trigger refuses updates to the fields that identify a build.

  4. 04
    build

    Lease one Linode, run rootless BuildKit against a generated (or repository-supplied) Dockerfile, stream the log to R2, destroy the VM. The lease row carries a hard expires_at so an orphan is reapable without control-plane memory.

  5. 05
    publish

    A trusted in-cluster Job pulls the tarball from R2 and pushes it into the private registry. The image is addressed by digest from here on.

  6. 06
    reclaim

    Delete the R2 tarball — but only after confirming the registry holds both the manifest blob and the repository revision link. The blob alone is shared across repositories, so a correct digest under the wrong repository would report 1 of 2 present.

  7. 07
    route

    Create or reuse the alias row for the hostname. Aliases are scoped by environment, so a preview build cannot repoint production.

  8. 08
    converge

    The reconciler reads desired state from Postgres and writes Deployment, Service, NetworkPolicy and one Ingress per alias. Level-triggered: it converges from whatever the cluster currently is.

  9. 09
    dns

    Upsert the proxied Cloudflare record. Platform subdomains sit under the wildcard and cost no custom hostname.

Detection: what it reads, and what it refuses

The detector recognises 10 runtimes — node, python, php, java, ruby, go, rust, static, hugo and repository-supplied docker — across roughly thirty framework shapes. It also refuses, which matters as much: a repository with no framework marker, a library that merely looks like an app, or a workspace root with no build script is turned away at detect, in seconds, without leasing a machine.

Empty is not the same as unknown

This is the single most repeated defect class in the project, and detection is where it bites hardest. A private repository read without a credential returns 404 — identical to a file that does not exist — so every marker probe came back empty and 36 of the operator's 49 repositories were undeployable with the blame pointed at their code. The same shape returned twice more: a rate-limit 429 read as an absent file, and a default branch guessed as master that raw.githubusercontent.com still served for a repository whose branches were main and two others. Null now means absent; unknown throws.

05

Build isolation

v1's build agent held the cluster kubeconfig and the platform-wide webhook secret, which is what turned a branch-name injection into full cluster compromise. v2's build VM is designed around the inverse question: what is the worst thing an attacker who fully owns this machine can do?

The VM holds

  • The tenant's own source
  • A short-lived git credential scoped to one repository, written to a 0600 credential file and deleted after the clone
  • Three presigned R2 URLs — log, metadata, image — each for one key
  • Build secrets via --mount=type=secret, which does not persist into a layer

The VM does not hold

  • Any kubeconfig
  • Any registry push credential
  • Any route to any cluster
  • Any other tenant's cache, source or secret
  • Any long-lived platform credential at all

The credential never appears in a URL. build/vm.ts refuses at render time to emit a clone URL of the form https://user:token@host/... — because git echoes the remote URL in its own error output, and that output is teed into a log served to team members.

Public versus private environment variables

Values prefixed NEXT_PUBLIC_, VITE_ and friends are public by definition — they end up readable in the shipped JavaScript either way — so they are passed as build args. Everything else is mounted as a build secret, which BuildKit keeps out of the image layers entirely. This split is inherited from v1, which got it right.

A defect this found

A Next.js app validating its environment at build time (@t3-oss/env-nextjs) failed with DATABASE_URL missing — and revealed that no environment variable reached the builder at all. Every app needing build-time config had been failing for a reason nothing reported.

Refs, not names

Every row carries an opaque ref generated by paas.gen_ref() — prj-e873172c1b7f, dpl-3c245e10f4bb, als-381e4107cf85. Refs are the public identifier everywhere in the API; internal UUIDs never leave the server. A trigger makes ref immutable.

This is the direct inversion of v1's root cause. Nothing addressable is a user-chosen mutable string, so there is no rename that can collide with another tenant's infrastructure.

Two independent gates

GRANT and RLS fail with near-identical errors

42501 permission denied for table versus new row violates row-level security policy. A full debugging round was lost to exactly that pair. Both gates are now stated explicitly in every migration, and it is the stated reason the multi-provider work kept one installations table rather than three: three tables would be six chances to repeat it, on the table whose entire job is authorization.

Privileged writes go through SECURITY DEFINER functions that re-check membership themselves — link_installation, rollback_project, charge_project_hour. A definer function that skips its own authorization is a privilege escalation with extra steps.

An except list cannot protect an address the policy never sees

The egress policy allows 0.0.0.0/0 with private ranges in an except list. The Kubernetes service ClusterIP 10.128.0.1 sits inside 10.0.0.0/8 and looks covered. It is not: kube-proxy DNATs the ClusterIP to the real endpoint before egress policy is evaluated, and on LKE that endpoint is a public address — so the policy sees a public destination and allows it.

Measured, not reasoned about: a busybox pod in a tenant namespace, under the same RuntimeClass as real workloads, completed a TCP connection to 10.128.0.1:443 while cross-tenant traffic to 10.2.0.33 was correctly refused. The API server CIDRs are now blocked explicitly. The private-range block is real for direct pod-to-pod traffic and does nothing for anything DNAT'd.

Kubernetes accepts a quota smaller than current usage

Existing pods keep running; only the next admission fails. So applying a ResourceQuota to a live namespace can silently create a namespace that cannot deploy again. The quota module measures the namespace first and reports whether the policy is enforceable before writing it.

Scale to zero

An activator holds the request while the pod is woken, so it is sleep rather than downtime. Idleness is measured, not assumed from elapsed time. It is built, proven, and currently opt-in and off — see §14 for why that is a commercial decision rather than a technical one.

The judges' verdict, kept verbatim because it still governs the design

An unauthenticated request that causes a pod to be scheduled is a DoS amplifier. Waking must be authenticated, rate-limited per hostname, and bounded by a per-tenant concurrent-wake budget.

One Cloudflare Origin CA certificate covers *.ahurasense.com to 2041. Platform subdomains consume no custom hostnames. Customer domains become Cloudflare custom hostnames and the UI shows the complete record set — the ownership TXT, the DCV TXT and the routing CNAME — each labelled with what it is for. A customer shown only the ownership TXT has been told how to prove they own the domain and nothing about how to make it answer.

Origin lockdown — verified in both directions

Four preconditions were checked rather than assumed: Traefik carries no ACME arguments, so nothing at the origin needs port 80 from outside Cloudflare; the firewall rules match Cloudflare's live list (15 v4, 7 v6, nothing missing, nothing extra); the firewall was attached to nothing; and all 26 A records are proxied — including two in other zones that the first check would have missed.

The apply script probes every live hostname, attaches, probes again, and detaches automatically if something that was answering has stopped. A revert nobody is awake to perform is not a revert. The first direct-access test returned 404, which looked like failure and was not — the same request timed out a minute later once the edge caught up.

Immutable deployments

These are the Vercel-class semantics, and each maps to one concrete mechanism.

CapabilityMechanism
Immutable deploymentsEvery build produces a digest-pinned image and a permanent URL. Nothing is ever rebuilt to promote.
Preview per branchA push to a non-production branch lands in its own preview environment, named after the raw branch so feature/foo and feature-foo stay distinct. Free, 48h from last push, Starter-sized, always 1 instance.
PromoteOne UPDATE of aliases.deployment_id. No rebuild.
RollbackThe same write, pointing at an earlier digest. v1's rollback depended on a Docker Hub tag nothing pruned or guaranteed.

Two defects previews found, both latent until the day they were not

The idempotency key was (project, sha) — correct only while every push builds production. A branch cut from the production head pushes a commit that is already deployed, so the key answered "already recorded" and the preview was never created. Silently, because 200 is what a successful retry looks like. Now keyed on (environment, sha).

And the serious one: deployFromRepo pointed every alias of the project at whatever built last. Correct while a project's hostnames all served one build — and a production outage the moment previews existed. Pushing any feature branch would have replaced production with that branch. Aliases are now scoped by environment.

Git providers

GitHub, GitLab and Bitbucket are all supported, and all three have been proven by deploying a real public repository end to end and serving a 200.

ProviderAuthClone usernameWebhookProven
GitHubApp installation token, minted per request, 1hx-access-tokenApp-level, all repos in the installation200
GitLabOAuth, refreshable token stored encryptedoauth2Per repository, shared token200
BitbucketOAuth, refreshable token stored encryptedx-token-authPer repository, HMAC secret200

The asymmetry is deliberate and worth naming

GitHub App tokens are minted from a private key and expire in an hour, so the platform stores no GitHub credential. GitLab and Bitbucket are OAuth: the platform holds a refreshable token for as long as the connection exists. Connecting GitLab gives us a durable credential to a customer's account and connecting GitHub does not. A breach of those columns is a different severity from a breach of the env-var table, and the columns are named so nobody has to infer that.

What was actually missing

The OAuth flows, webhook receivers, per-provider clients and multi-provider columns all existed before this work. What did not exist was any code path that named the provider — so a GitLab connection could be recorded, its pushes received, and then the build would try to clone it from github.com. Three hardcodes, each load-bearing:

  • the clone URL, built unconditionally as https://github.com/<repo>.git;
  • provider: "github" on both project-creation paths;
  • the build VM's credential file, which named github.com as the host.

That last one is the subtle one. git matches a credential entry by host, so a file naming github.com is silently ignored when cloning gitlab.com — and the clone then fails as "authentication failed" on a token that is perfectly good. The host is now derived from the clone URL itself, so the credential and the remote cannot disagree.

Bitbucket's anonymous budget is sixty calls an hour

Detection probed about forty marker files, one call each — so one deploy consumed most of an hour and the next failed. The fix was two-sided: a 429 now throws instead of returning null (null means absent to detection, which would have told a customer to add a package.json they already had), and the root directory is listed in one call so absent files cost nothing. GitHub is deliberately exempt — it reads through raw.githubusercontent.com, which does not share that budget.

11

Environment variables

Values are encrypted with AES-256-GCM under a per-project key derived by HKDF from a master key that lives outside every repository. The database stores ciphertext and a DEK id, never plaintext. Provider OAuth tokens use the same primitive in a separate HKDF context, so an env-var ciphertext fed to the connection decrypt is refused by scheme name rather than failing somewhere less legible.

At runtime, values are injected via envFrom — which Kubernetes reads once, at container start. That single fact drives the product behaviour: changing an environment variable does not affect a running app until it is redeployed, and the UI says so plainly rather than claiming a restart it does not perform.

A UI that lied, caught by reading its own server's note

The editor said "restarting to apply". Nothing reconciles on an env change. The server-side comment next to the write had been correct the whole time — the interface had drifted away from it.

12

Metering and billing

Billing is live as of 28 Aug 2026. The first real pass charged 5 projects $0.047945 for the hour; a second pass charged $0.000000 and reported all five already-charged.

Verified against balances, not against the sweep's own report

777.151506 → 777.122739 is exactly three projects, and 656042108.091267 → 656042108.072089 is exactly two. A sweep that says it charged and a balance that moved are different claims — and v1's defining billing defect was precisely a system that reported success while the meter did something else.

Three mechanisms carry the v1 lessons directly:

  • Idempotent by construction. UNIQUE (project_id, period_start) means a retry, a double cron fire or a concurrent worker cannot bill the same hour twice.
  • Teardown was enabled first and had converged to zero before metering was turned on. Billing a project whose pods were never torn down is v1's $543.17 defect exactly.
  • Usage samples outlive the project. The final bill and any dispute about it both arrive after deletion, so the facts cannot be deleted with the row.

Customers can see what they were charged at GET /api/v2/projects/{ref}/usage. The summing lives in lib/paas/usage.ts because that is the part that fails quietly: auth and a query fail with a status code, whereas arithmetic produces something that looks like a bill. Number(null) is 0 and Number("abc") is NaN, which survives Math.round to serialise as JSON null — a blank where a figure belongs, with nothing reporting a fault. An unreadable amount is counted, never added.

The number the whole model rests on

Warm fraction measured 1.0

Across three independent measurements, every app holds a pod all day at 2–3 millicores with zero requests. That is the ~$52k/month model at 10,000 apps, not the $18–20k the plan assumes. Scale-to-zero is built and proven but opt-in and off — turning it on is the single largest lever on unit economics, and it trades a cold start on the first request for most of that difference. A product decision, not a technical one.

Two measurement corrections got the cost model to where it is, and both moved it in the expensive direction: the kubelet reserves 24.5% of a node before any pod schedules, and the gVisor sandbox charge was declared at 128Mi against 42 MiB measured. Cutting the declaration to 64Mi took density from 89 to 99 pods per node. Prices did not move with the second correction — the margin sits as buffer, because repricing twice against one number spends confidence in the list.

The earlier estimate of "~65 tenant pods/node" was really 42. The lesson recorded from that: the sentences that go stale are the ones asserting a STATE rather than a RULE. "65 pods/node" is a state and rotted in a day; "the transitive closure is the credential surface" is a rule and has not.

What the sweep found that no template would have

Each of these was a real defect reached by deploying something, not by reading code:

  • Every static site crash-looped — on an nginx pidfile substitution matching a path nginx no longer uses. Hidden because everything deployed until then was a Node server or a repo-supplied Dockerfile.
  • No repository without a lockfile could build. Every frozen-install flag is a hard error without one, and the generated Dockerfile always chose the frozen form.
  • No monorepo could install — the deps stage copied only the root manifest, so a workspace dependency could not resolve.
  • No native dependency could compile — no python3, make or g++ in the image, so anything falling back from a prebuilt binary died inside node-gyp.
  • Public environment variables reached nothing — not the bundle, not the container. The reconciler skipped them as already baked in, and nothing baked them.
  • Gatsby and Docusaurus were not detected at all and ran as generic Node apps with no server to start.
  • The Node major was hardcoded to 22 and every pin a repository offered was ignored.
  • A Next.js app with output: 'export' crash-looped on every provider — next start cannot serve an exported build, and detection called it a node app.

And one regression caused, then caught

Honouring .nvmrc as a hard pin broke sveltejs/realworld, which had been serving: its .nvmrc says 20 while a package in its tree demands >=22.12.0. engines.node is published and enforced; .nvmrc is a local note that goes stale silently. So engines decides — including downward — and .nvmrc may only raise the floor. This is the argument for keeping green targets in the sweep instead of retiring them.

How it is tested

1,079 tests, 0 failing. They run on Node's own test runner (npm run test:paas) with no framework dependency, so the whole lib/paas tree stays dependency-free. 73 test modules sit beside the 79 source modules they cover.

Three ways a green suite lies, all three met here

FailureWhat happened
A glob that matches nothing npm test was vitest with include: ['tests/**'], and every deploy-v2 test lives in lib/paas/**. No script ran them. Every regression guard written during the framework sweep — including ones written because a bug had already shipped once — sat unrun while the suite reported green.
A runner that dies before it starts tsx cannot compile a top-level await to CommonJS. The batch script had one, never reached a single repository — and because the run was piped, the pipeline's exit code was reported instead of the script's. Two independent green signals, neither of which had run anything.
A checker that exits 0 on broken input node --experimental-strip-types --check exits 0 on an unterminated string literal. Every "parses clean" claim made with that command was weaker than stated.

The working rules that came out of that:

  • Verify by running, not by reading. Three unpiped runs before quoting an exit code.
  • Skip is not pass. Live-enum mirror tests skip when the database is unreachable — skip means "could not check", pass means "checked and fine", and conflating them is how a suite goes green while asserting nothing.
  • Prove the guard by breaking it. A new guard is mutation-tested: remove it and the test must fail. The rate-limit guard in §10 was proven exactly this way.
  • A proof that calls a working feature a bug is how a red line stops being read. A proof script printed "non-production branch DEPLOYS — BUG" on every run after previews shipped.

Three ways a guard goes vacuous, and they look identical from outside

A count that stays true while coverage is lost; a check placed above the branch it was meant to catch; and a CASE with no ELSE in a CHECK constraint — which returns NULL for an unmatched value, and a CHECK constraint passes on NULL. Adding a fourth git provider would have silently switched the account-name grammar off for it: still listed, still green, enforcing nothing. That constraint now ends else false.
