VULN-001: .env File Contains ALL Production Secrets in Plaintext
------------------------------------------------------------------------------
Severity:    CRITICAL
Category:    Secrets Management / Data Exposure
File:        .env (105 lines, present in working directory)

Description:
  The .env file is present on disk and contains every production secret for
  the entire platform. While .env is listed in .gitignore, the file exists
  in the working directory and any accidental `git add -A`, CI artifact leak,
  or filesystem access exposes total platform compromise.

  Exposed credentials include:
    - SUPABASE_SERVICE_ROLE_KEY (bypasses all RLS, full DB read/write)
    - OPENAI_API_KEY, OPENROUTER_API_KEY
    - STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET
    - REDIS_URL (with password: Pankajsoni1155@172.105.39.76:6379)
    - DIGITAL_OCEAN_TOKEN
    - CLOUDFLARE_API_TOKEN, CLOUDFLARE_API_TOKEN_SPECTRUM
    - JENKINS_URL (with admin:password embedded in URL)
    - GITLAB_CLIENT_SECRET, BITBUCKET_CLIENT_SECRET
    - ENCRYPTION_KEY
    - KUBE_CONFIG_STRING (full base64 kubeconfig with cluster-admin certs)
    - PTERO_API_KEY (Pterodactyl panel admin)
    - RESEND_API_KEY
    - NAMECOM_API_TOKEN

Exploit Scenario:
  An attacker obtaining this single file gains root access to every
  infrastructure component: Supabase (all user data), Kubernetes (all
  workloads), Proxmox (all VMs), Stripe (billing manipulation), DNS
  (domain hijacking), Jenkins (arbitrary code execution), and more.

Remediation:
  1. Rotate ALL credentials immediately
  2. Use a secrets manager (HashiCorp Vault, AWS Secrets Manager, Doppler)
  3. Never store secrets in flat files on production servers
  4. Implement secret scanning in CI/CD pipeline (e.g., gitleaks, trufflehog)

VULN-002: Bitbucket Webhook Signature Validation Accepts ALL Requests
------------------------------------------------------------------------------
Severity:    CRITICAL
Category:    Broken Authentication / Webhook Forgery
File:        lib/webhooks/bitbucket.ts
Lines:       19-45

Description:
  The Bitbucket webhook signature validation function returns true (accept)
  in every error case instead of rejecting:

    - No secret configured     -> return true  (should reject)
    - No signature header      -> return true  (should reject)
    - Signature length mismatch -> return true (should reject)

  Code:
    static validateSignature(...): boolean {
      if (!secret) {
        console.warn('No secret configured, skipping signature validation');
        return true;   // BUG: accepts unsigned webhooks
      }
      if (!signature) {
        console.warn('No signature header present, skipping validation');
        return true;   // BUG: accepts missing signatures
      }
      if (sigBuffer.length !== digBuffer.length) {
        console.warn('Signature length mismatch, skipping strict validation');
        return true;   // BUG: accepts invalid signatures
      }
    }

Exploit Scenario:
  Any attacker can send forged Bitbucket webhook payloads to
  POST /api/webhooks/git/bitbucket to trigger arbitrary deployments.
  This could deploy malicious code to production Kubernetes clusters.

Remediation:
  Change all `return true` in error cases to `return false`.
  A webhook with no secret, no signature, or wrong signature must be rejected.

VULN-004: Middleware Auth Bypass for AI Agent Routes
------------------------------------------------------------------------------
Severity:    CRITICAL
Category:    Broken Access Control / Authentication Bypass
File:        middleware.ts
Lines:       120-131

Description:
  The Next.js middleware completely skips all checks (session refresh,
  rate limiting) for several route patterns based solely on the presence
  of an Authorization header -- regardless of its value:

    if (pathname.startsWith('/api/ai-agents/') && pathname.endsWith('/test')) {
      return NextResponse.next();  // COMPLETE BYPASS
    }
    if (pathname.startsWith('/api/ai-agents') && hasAuthorizationHeader) {
      return NextResponse.next();  // ANY Authorization header works
    }
    if (pathname.startsWith('/api/knowledge-bases') && hasAuthorizationHeader) {
      return NextResponse.next();  // ANY Authorization header works
    }
    if (pathname.startsWith('/api/v1/agents/') && pathname.endsWith('/chat')) {
      return NextResponse.next();  // COMPLETE BYPASS
    }

Exploit Scenario:
  curl -H "Authorization: Bearer garbage" https://target/api/ai-agents/...

  This bypasses all middleware-level protections. If any downstream route
  handler trusts that middleware has already validated the session, it's
  wide open to unauthenticated access.

Remediation:
  Middleware should never skip entirely based on header presence alone.
  Move the SSE bypass to only the specific streaming routes that need it,
  and still validate the token value. At minimum, check that the token
  is non-empty and well-formed before bypassing.

Description:
  REDIS_URL="redis://:Pankajsoni1155@172.105.39.76:6379/0"

    - No TLS encryption (redis:// not rediss://)
    - Default port 6379

Exploit Scenario:

  manipulate rate limits, inject malicious BullMQ jobs, or use Redis

VULN-008: Inconsistent Admin Authorization -- Three Different Patterns
------------------------------------------------------------------------------
Severity:    HIGH
Category:    Broken Access Control / Privilege Escalation
Files:       lib/supabase/auth.ts:22-71
             app/api/admin/users/route.ts:5-26
             app/api/admin/proxmox/vms/create/route.ts:143-168
             (and ~24 other admin route files)

Description:
  Three different admin check implementations exist across 27 admin routes:

  Pattern A - requireAdmin() from lib/supabase/auth.ts:
    Checks ADMIN_EMAILS env var first, falls back to user_profiles.roles.
    Used by: audit-logs, ai-agents stats, database-options, proxmox hosts

  Pattern B - inline checkAdminAuth():
    Checks user_profiles.roles.includes("admin") ONLY. Ignores ADMIN_EMAILS.
    Used by: users, coupons, databases, cluster-metrics, ai-agents models,
    network-ddos, kubernetes delete (~20 routes)

  Pattern C - requireAdmin() in proxmox/vms/create:
    Checks ADMIN_EMAILS env var ONLY. No user_profiles fallback.
    Used by: proxmox VM creation

  Additionally, ADMIN_EMAILS is NOT set in the .env file, which means:
    - Pattern A falls through to user_profiles check (works)
    - Pattern C allows ALL authenticated users through (if env var is empty
      and adminEmails array has length 0, condition on line 159 is skipped)

Exploit Scenario:
  1. If a user can modify their own user_profiles.roles (RLS misconfiguration),
     they gain admin access to all Pattern B routes
  2. The proxmox VM create route (Pattern C) may be accessible to non-admins
     when ADMIN_EMAILS is unset, depending on the empty-array logic

Remediation:
  Consolidate all 27 admin routes to use a single requireAdmin() function.
  Fix the empty ADMIN_EMAILS fallback logic to be explicit.

VULN-010: In-Memory Rate Limiting -- Bypassable in Multi-Instance Deployment
------------------------------------------------------------------------------
Severity:    HIGH
Category:    Insufficient Rate Limiting
Files:       middleware.ts:24 (ipStore = new Map())
             lib/rate-limit.ts:15 (store = new Map())

Description:
  IP-based rate limiting in the middleware and the generic rate limiter both
  use in-memory Map objects:

    const ipStore = new Map<string, IpRecord>();  // middleware.ts:24
    const store = new Map<string, RateLimitStore>(); // rate-limit.ts:15

  Problems:
    1. Multi-instance: In Kubernetes/PM2, each pod has its own Map.
       Requests distributed across N pods get N times the rate limit.
    2. Restart: Server restart clears all rate limit state.
    3. Memory leak: No bounded size on the Maps. Slow probabilistic
       cleanup (10% chance per request in rate-limit.ts:70).

  Note: The per-user rate limiter (lib/cooldown/userbased.ts) correctly
  uses Redis. Only the middleware-level IP limiter is affected.

Remediation:
  Move IP rate limiting to Redis/Upstash, consistent with the per-user
  rate limiter. The code already has a comment acknowledging this:
  "use Redis/Upstash for multi-instance in future" (middleware.ts:23).

VULN-011: IP Spoofing via X-Forwarded-For Header
------------------------------------------------------------------------------
Severity:    HIGH
Category:    Rate Limit Bypass / Log Forgery
Files:       middleware.ts:27-31
             lib/rate-limit.ts:34-36
             lib/audit/context.ts:28
             (~10 additional locations)

Description:
  Client IP is derived from the X-Forwarded-For request header:

    function getClientIp(req: NextRequest): string {
      return (
        req.headers.get("x-forwarded-for")?.split(",")[0]?.trim() ||
        req.headers.get("x-real-ip") ||
        "unknown"
      );
    }

  If the application is not behind a trusted reverse proxy that strips
  and overwrites X-Forwarded-For, any client can set this header to an
  arbitrary value, completely bypassing all IP-based rate limiting.

  Additionally, audit logs (lib/audit/context.ts) record this spoofable
  IP, making forensic analysis unreliable.

Exploit Scenario:
  curl -H "X-Forwarded-For: 1.2.3.4" https://target/api/auth/signin
  curl -H "X-Forwarded-For: 5.6.7.8" https://target/api/auth/signin
  (each request appears as a different IP, bypassing rate limits)

Remediation:
  1. Configure the reverse proxy (nginx, Cloudflare) to set a trusted
     client IP header
  2. Only trust X-Forwarded-For from known proxy IPs
  3. Fall back to connection remote address, not "unknown"

VULN-012: MFA Enrollment Auto-Deletes Verified Factors
------------------------------------------------------------------------------
Severity:    HIGH
Category:    Authentication Bypass
File:        app/api/auth/mfa/enroll/route.ts
Lines:       44-76

Description:
  When a user hits the maximum MFA factor limit, the enrollment endpoint
  automatically deletes the oldest verified factor to make room:

    // Remove unverified factors first
    for (const factor of factors.data.totp) {
      if (factor.status === "unverified") {
        await supabase.auth.mfa.unenroll({ factorId: factor.id });
      }
    }

    // If still hitting limit, remove oldest verified factor
    if (enrollError?.message?.includes("Maximum number of verified factors")) {
      // ... removes oldest verified factor
    }

Exploit Scenario:
  An attacker who compromises a user's session (e.g., via session fixation
  or XSS) can call the MFA enroll endpoint to silently remove the victim's
  legitimate MFA factor and enroll their own. The victim won't know their
  MFA was replaced until their next login attempt.

Remediation:
  1. Never auto-delete verified MFA factors
  2. Return an error if the user has max factors
  3. Require current MFA verification before deleting any existing factor
  4. Send email notification when MFA factors change

VULN-013: Service Role Key Used Extensively Without Row-Level Scoping
------------------------------------------------------------------------------
Severity:    HIGH
Category:    Broken Access Control / IDOR Risk
File:        lib/supabase/server.ts:104-112

Description:
  createWorkerClient() uses SUPABASE_SERVICE_ROLE_KEY which bypasses ALL
  Supabase Row-Level Security (RLS) policies:

    export async function createWorkerClient() {
      return clientWorker<Database>(
        process.env.SUPABASE_URL!,
        process.env.SUPABASE_SERVICE_ROLE_KEY!, // bypasses all RLS
        { auth: { persistSession: false, autoRefreshToken: false } }
      );
    }

  This client is used in ~40+ query functions across lib/supabase/queries.ts.
  While some API routes verify resource ownership before calling these
  functions, the service role client has unrestricted access to all tables
  and all rows.

  service-role query without first validating ownership, it creates an
  Insecure Direct Object Reference (IDOR) vulnerability.

Remediation:
  1. Prefer user-scoped Supabase clients (anon key + user JWT) for queries
     that should respect RLS
  2. Only use service role for operations that genuinely require elevated access
  3. Always verify resource ownership at the API layer before service-role ops
  4. Audit all 40+ usages for missing ownership checks

VULN-015: No CSRF Protection on State-Changing Endpoints
------------------------------------------------------------------------------
Severity:    HIGH
Category:    Cross-Site Request Forgery
Files:       All app/api/services/*/route.ts POST handlers

Description:
  Next.js API routes don't have built-in CSRF protection. State-changing
  endpoints (VM create, database delete, app delete, billing operations)
  accept JSON bodies via POST with cookie-based authentication.

  While SameSite=Lax cookies provide partial mitigation, modern fetch()
  requests with credentials: 'include' from cross-origin pages may still
  succeed depending on browser behavior and CORS configuration.

  No custom anti-CSRF header or token is required by any endpoint.

Remediation:
  1. Add CSRF token validation on all state-changing endpoints
  2. OR require a custom header (e.g., X-Requested-With) that triggers
     CORS preflight and cannot be sent cross-origin without CORS approval
  3. Consider using SameSite=Strict for session cookies

VULN-016: Missing Content-Security-Policy Header
------------------------------------------------------------------------------
Severity:    MEDIUM
Category:    XSS Defense / Security Headers
File:        next.config.ts:11-43

Description:
  Good security headers are present:
    - X-Frame-Options: DENY
    - X-Content-Type-Options: nosniff
    - Strict-Transport-Security (HSTS with preload)

    - X-XSS-Protection: 1; mode=block

    default-src 'self';
    script-src 'self';
    style-src 'self' 'unsafe-inline';
    img-src 'self' https://samatva.blr1.cdn.digitaloceanspaces.com https://flagcdn.com;
    connect-src 'self' https://xafjjpgazdxhktpfeuri.supabase.co;
